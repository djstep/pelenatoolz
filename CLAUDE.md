# Правила проекта PELENA (Film_Prod)

## О проекте
SaaS для управления кинопроизводством: сценарий, либретто, кастинг, скаут, КПП, вызывные, отчёты смены, смета, финансы, договоры. Мультипроектная: пользователь одного проекта не должен видеть и менять данные другого.

Стек: Next.js 16 (App Router, server actions), React 19, TypeScript, Prisma 6, PostgreSQL (Neon), Auth.js 5. Хостинг сейчас Vercel, позже переезд на VPS в РФ.

Владелец проекта не программист. Объясняй по-русски и просто.

## Запрещено без прямого разрешения владельца в чате
- База в Neon — временная тестовая, реальных данных там нет. Сайт на Vercel подключён к ней же.
- Схему менять только через файлы миграций (prisma migrate dev / migrate deploy). prisma db push не использовать никогда. Перед применением миграции показать prisma migrate status.
- prisma migrate reset и массовое удаление данных — только с явного разрешения.
- git push, слияние в main, удаление веток.
- Удаление файлов, не созданных в текущей задаче.
- Установка новых пакетов — сначала спросить.

## Задачи
- docs/tasks/wave-*.md — ТЗ волн доработок. Отчёты по волнам — docs/tasks/WAVE_*_REPORT.md.

## Как работать
- Одна задача — один шаг. После шага остановись, коротко отчитайся и жди «дальше».
- Меняй только то, что относится к задаче. Заметил другую проблему — запиши в отчёт, не чини.
- Никакого рефакторинга «заодно».
- Перед завершением шага: `npx tsc --noEmit` (0 ошибок), `npx eslint` по изменённым файлам (без новых ошибок), `npm run build` (проходит).
- Коммить в текущую рабочую ветку после каждого завершённого шага, если владелец подтвердил.

## Параллельная работа (субагенты)
### 1. Роль главной сессии
Ты — координатор. Сама код не пишешь, файлы не правишь, тесты не гоняешь, миграции не применяешь. Твоя работа: понять задачу, разбить на части, раздать форкам и агентам, проверить их результаты (через reviewer), собрать и вывести мне короткий итог. Мелкие проверки состояния (git status, git log, db:whoami) — можно самой.
Когда я спрашиваю подробности по работе — спроси у того форка/агента, который её делал (продолжи его через SendMessage), не отвечай по догадке.

### 2. Кто что делает
- Основная разработка — один dev-форк на шаг волны (форк, чтобы у него был весь контекст разговора). Он пишет код, применяет миграции на dev/e2e, гоняет проверки шага. Одновременно код пишет только один исполнитель — никаких параллельных правок, worktree не нужен. Внутри шага продолжай тот же форк через SendMessage, новый не запускай. На новый шаг волны — новый форк.
- runner (sonnet, усилие среднее, чтение + Bash) — поиск по коду, списки файлов, прогоны тестов и сбор результатов, скриншоты. Можно параллельно с dev-форком, если не трогают одно и то же.
- reviewer (модель как у главной, усилие высокое, только чтение) — после каждого шага независимая проверка: соответствие заданию, права, безопасность, данные. Не видел, как писался код. Его замечания — dev-форку на исправление, мне — итог проверки.
Файлы агентов в .claude/agents/; точные имена полей заголовка (модель, усилие, инструменты) сверь с документацией Claude Code. Если усилие в описании агента задать нельзя — скажи прямо.

### 3. Ограничения для всех исполнителей
- e2e: одновременно только один прогон на одну базу.
- У e2e своя база: `npm run e2e`, сид, хелперы и сайт для тестов берут адрес только из `E2E_DATABASE_URL` и `E2E_DIRECT_URL` в `.env.e2e`. Без этих переменных, на базе не из `E2E_DATABASE_ENDPOINTS` (`src/shared/db/e2e-database-guard.ts`) или на базе из `.env` e2e не запускается, отката на `.env` нет. Сайт поднимает сам Playwright на порту 3100: порт должен быть свободен, `npm run dev` в этой папке на время e2e остановить. С заглушкой дисков (PowerShell): `$env:E2E_CLOUD_STUB_URL="http://127.0.0.1:4510"; npm run e2e`.
- Миграции на базе e2e: `npm run db:status:e2e` показывает состояние, `npm run db:migrate:e2e` применяет только готовые файлы миграций. Обе команды идут по `E2E_DIRECT_URL` с той же проверкой базы, что у e2e, и других аргументов не принимают. Вдобавок в `E2E_DIRECT_URL` должен быть прямой адрес: адрес через пул даёт отказ.
- Миграции и действия с базой — только dev-форк, по одной, только dev/e2e.
- Прод не трогать, push не делать, строки подключения и пароли не выводить — передавай эти правила в задание каждому форку и агенту.
- Шаги волны — строго по одному: после шага стоп и мой ответ «дальше».

### 4. Мой вывод
Мне — только итог: что сделано, отступления, что проверил reviewer и что он нашёл, вопросы ко мне, что дальше. Одна строка на каждого запущенного исполнителя: кто (dev-форк/runner/reviewer), модель, зачем. Без логов и пересказа кода.

### 5. Замки в .claude/settings.json
- deny: git push в любом виде (push делаю сам); чтение .env и .env.* — Read и команды cat/type/Get-Content/more.
- скрипт npm run db:whoami: печатает только хост (ep-...) и имя базы, без пользователя и пароля. Адрес базы проверять только им.
Если ещё какое-то правило отсюда можно сделать запретом в settings.json — предложи списком, без внедрения.

## Правила безопасности кода
- `projectId` всегда из проверенного контекста (`requireProjectContext` / `requireProjectAccess`), никогда из данных браузера.
- Любой id из браузера, который пишется в базу или по которому меняется запись, проверять на принадлежность проекту через `assertInProject` (`src/features/memberships/assert-in-project.ts`) до первой записи.
- Ошибку «чужой объект» распознавать через `isNotInProjectError`, а не сравнением текста.
- В файлах `"use server"` каждая экспортированная функция — публичная точка доступа. Без проверки входа и прав там ничего не экспортировать.
- Аудит изменений — через существующий `recordAudit` / `auditMutation`.
