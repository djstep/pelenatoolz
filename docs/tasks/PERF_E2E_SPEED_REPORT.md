## Что сделано

1. **Группы файлов в `playwright.config.ts`.**
   - `read` — 7 файлов, которые только читают: `a0`, `a1`, `a2`, `c2`, `c7`, `d1`, `d2`. Идут в 4 потока.
   - `write` — всё остальное, по очереди, только после `read`. Новый файл попадает сюда сам.
   - `drive` — 8 файлов Диска: `c3`, `c4`, `c5`, `c6`, `c9`, `c10`, `c11`, `c12`.
2. **`npm run e2e:drive`** — отдельная команда. В `CLAUDE.md` вписано: запускать перед каждым слиянием в `main` и в конце волны.
3. **`a1` разбит на потоки внутри файла.** Без этого он один держал группу `read` 6 минут.
4. **Утверждённая версия вызывного дня 1 — в сиде** (`scripts/e2e-seed.ts`, `e2e/helpers/seed-approved-call-sheet.ts`). Снимок собирает настоящий код сайта, сам вызывной остаётся черновиком следующей версии, как после «Внести изменения». Повторный запуск сида ничего не добавляет.
5. **Проверка снимка в `a1`** теперь смотрит дни 1 и 2 и падает, если версий нет. Раньше она молча ничего не проверяла, если версий ещё не было. Новый порядок делал это обычным случаем: `a1` идёт раньше `c1`.
6. **Заглушка дисков включена всегда.** Без неё файлы Диска пропускались бы, и `e2e:drive` был бы зелёным, ничего не проверив.

## Отступления

- Упал файл из `read` — `write` не идёт, это правило Playwright. Полная картина в таком случае: `npm run e2e -- --no-deps`.
- Запуск одного файла теперь с флагом: `npm run e2e -- --no-deps c15`. Без флага сначала пройдёт вся группа `read`.
- `c1` создаёт вызывной дня 2 кнопкой, поэтому утверждённая версия в сиде стоит на дне 1, а не на дне 2.

## Что не проверялось

- **`e2e:drive` на пустой базе.** Прогон шёл на базе, где уже есть данные от прежних прогонов, в том числе вызывной дня 2 из `c1`. Файл `c6` открывает вызывной дня 2, на новой базе его нет, пока не прошёл `c1`. Проверим на локальной базе; если упадёт, порядок будет: сначала `npm run e2e`, потом `npm run e2e:drive`.
- **Сид на пустой базе.** Прошёл на существующем проекте, создание проекта с нуля в этой задаче не запускалось: `--reset` стирает проект, разрешения на него не было.

## Подготовка к локальному Postgres

Инструкция: `docs/tasks/LOCAL_POSTGRES_SETUP.md`. Владелец ставит Postgres сам.

- В список сида добавлены локальные `pelena_dev` и `pelena_e2e`, в список e2e — только `pelena_e2e`. База определяется по серверу и имени: другая база на этой машине получает отказ.
- Обе строки `.env.e2e` теперь обязаны вести в одну базу, иначе миграции могли бы уйти в Neon, а сайт работать на локальной.
- Вне Neon база в `.env` сравнивается с базой e2e только по имени, без сервера: на одну машину ведёт много адресов.
- `c14` больше не ждёт имя Neon-сервера в выводе скрипта.
- Сид печатает сервер через `databaseHost`: прежняя строка при `@` в пароле могла вывести его часть.
