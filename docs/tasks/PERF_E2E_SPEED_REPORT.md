# Отчёт: perf/e2e-speed — скорость e2e

Ветка `perf/e2e-speed` от `main`. Push делает владелец.

## Итог

| Что | Было, Neon, один поток | Группы и потоки, Neon | Локальный Postgres |
|---|---|---|---|
| `npm run e2e` | 69 мин 15 с, все 323 теста | 30 мин 16 с, 269 тестов | **4 мин 46 с**, 269 тестов |
| `npm run e2e:drive` | входил в общий прогон | 26 мин 30 с, 54 теста | **2 мин 24 с**, 54 теста |
| Оба вместе | 69 мин 15 с | 56 мин 46 с | **7 мин 10 с** |

Локальный Postgres дал ускорение в 6 раз для `e2e` и в 11 раз для `e2e:drive`, а с начала задачи общее время сократилось почти в 6 раз.

Замер на локальной базе, коммит `7e13ba2`:

- `npm run e2e`: 238 прошло, 0 упало, 31 служебный пропущен (`d3`–`d6`, только с отдельными переменными). Decimal: 0.
- `npm run e2e:drive`: 54 прошло, 0 упало, 0 пропущено. Decimal: 0.
- Повторов не было. `npm test`: 1430 из 1430. `npx tsc --noEmit`: 0. `npm run build` проходит.

Цифры в колонке «Neon» сняты на коммите `440a213`. Все файлы по очереди шли 69 мин.

Самые долгие файлы на локальной базе: `a1` 93 с, `c3` 54 с, `c14` 50 с, `c18` 42 с, `c19` 35 с. `a1` идёт в 4 потока, поэтому группа `read` занимает меньше этой суммы.

## Что сделано

1. **Группы файлов в `playwright.config.ts`.**
   - `read` — 7 файлов, которые только читают: `a0`, `a1`, `a2`, `c2`, `c7`, `d1`, `d2`. Идут в 4 потока.
   - `write` — всё остальное, по очереди, только после `read`. Новый файл попадает сюда сам.
   - `drive` — 8 файлов Диска: `c3`, `c4`, `c5`, `c6`, `c9`, `c10`, `c11`, `c12`.
2. **`npm run e2e:drive`** — отдельная команда. В `CLAUDE.md` вписано: запускать перед каждым слиянием в `main` и в конце волны.
3. **`a1` разбит на потоки внутри файла.** Без этого он один держал группу `read` 6 минут.
4. **Утверждённая версия вызывного дня 1 — в сиде** (`scripts/e2e-seed.ts`, `e2e/helpers/seed-approved-call-sheet.ts`). Снимок собирает настоящий код сайта, сам вызывной остаётся черновиком следующей версии, как после «Внести изменения». Повторный запуск сида ничего не добавляет.
5. **Проверка снимка в `a1`** теперь смотрит дни 1 и 2 и падает, если версий нет. Раньше она молча ничего не проверяла, если версий ещё не было. Новый порядок делал это обычным случаем: `a1` идёт раньше `c1`.
6. **Заглушка дисков включена всегда.** Без неё файлы Диска пропускались бы, и `e2e:drive` был бы зелёным, ничего не проверив.

## Отступления

- Упал файл из `read` — `write` не идёт, это правило Playwright. Полная картина в таком случае: `npm run e2e -- --no-deps`.
- Запуск одного файла теперь с флагом: `npm run e2e -- --no-deps c15`. Без флага сначала пройдёт вся группа `read`.
- `c1` создаёт вызывной дня 2 кнопкой, поэтому утверждённая версия в сиде стоит на дне 1, а не на дне 2.

## Проверки на пустой базе

Порядок: `migrate deploy` на обе базы, сид дважды, `e2e:drive`, `e2e`, снова `e2e:drive`.

- **Миграции.** 72 из 72 применились на `pelena_e2e` и `pelena_dev`.
- **Сид с нуля.** Создал 5 пользователей, 2 проекта, 5 съёмочных дней и утверждённую версию вызывного. Повторный запуск ничего не добавил.
- **`e2e:drive` без предыдущего `e2e`.** 54 из 54 за 2 мин 25 с. Опасение про `c6` не подтвердилось: выгрузка дня 2 не требует сохранённого вызывного, тест находит файл в базе. Запускать `e2e:drive` можно в любом порядке.
- **Чужой проект для `a2`.** Теперь его создаёт сид, владелец — отдельный пользователь. Все 3 проверки выполнились, а не пропустились.
- **Настройки базы.** Отличие от Neon одно: `LC_COLLATE` и `LC_CTYPE` равны `C`, а не `C.UTF-8`. Запрос на локальной базе дал правильный регистр русских букв, включая `ё`, и порядок по кодам символов, как у `builtin C.UTF-8`. На Neon тот же запрос не запускался.

Записано, не чинилось: `pelena_dev` пустая, на локальном сайте нужно зарегистрироваться заново.

## Подготовка к локальному Postgres

Инструкция: `docs/tasks/LOCAL_POSTGRES_SETUP.md`. Владелец поставил Postgres сам.

- В список сида добавлены локальные `pelena_dev` и `pelena_e2e`, в список e2e — только `pelena_e2e`. База определяется по серверу и имени: другая база на этой машине получает отказ.
- Обе строки `.env.e2e` теперь обязаны вести в одну базу, иначе миграции могли бы уйти в Neon, а сайт работать на локальной.
- Вне Neon база в `.env` сравнивается с базой e2e только по имени, без сервера: на одну машину ведёт много адресов.
- `c14` больше не ждёт имя Neon-сервера в выводе скрипта.
- Сид печатает сервер через `databaseHost`: прежняя строка при `@` в пароле могла вывести его часть.

reviewer, один проход: критичных нет, 3 важных исправлены. Правки он не перепроверял. В обход проверки через строку подключения чужая база не проходит; это проверено чтением, разбор строки движком Prisma — по памяти об исходниках, запуском не подтверждён.

**Записано, не чинилось:**
- Neon-адрес с параметром `?host=` проверкой не ловится: параметры смотрятся только у локальных адресов. Было до шага, владелец просил Neon не менять.
- Порт локальной базы не проверяется: установщик может выдать другой. Второй Postgres на этой машине с тем же именем базы пройдёт.

## Откуда время

Основная причина — обращения к базе. Один запрос к базе e2e в Neon (Лондон) идёт около 160 мс. Переход на локальную базу это подтвердил. Таблицы ниже сняты на Neon.

| Сравнение | `next dev` | `next start` |
|---|---|---|
| `c15` | 87 с | 87 с |
| `a1` | 373 с | 331 с |
| `c18` | 280 с | 269 с |

Поэтому `next start` выигрыша не даёт, а заглушка дисков в production отключена. Лишних пауз почти нет: фиксированные ожидания дают меньше 15 с на весь прогон.

## Страницы и запросы к базе (мера 6, отдельной задачей)

Замер: счётчик транзакций Postgres до и после одного открытия страницы под продюсером, на прогретом `next dev`. Одно обращение здесь — одна транзакция, поэтому реальных запросов может быть больше. Причины не подтверждены замером, это гипотезы по чтению кода.

| Страница | Время | Обращений к базе | Гипотеза причины |
|---|---|---:|---|
| Вызывной дня | 12,0 с | 181 | Вложенные `include` дают отдельный запрос на каждую связь: `relationJoins` не включён. 12 загрузчиков запускаются разом. |
| Лист вызывного (`/sheet`) | 9,7 с | 112 | Та же сборка данных дня: `getShootDayDocument`, `getCallSheetForDay`, `getCallSheetElementsEditor`, плюс проверка доступа. |
| Обзор проекта | 2,0 с | 32 | Отдельные подсчёты по разделам. |
| Команда | 2,9 с | 29 | Вход и доступ загружаются заново. |
| Кастинг | 3,0 с | 28 | Вход и доступ загружаются заново. |
| Профиль | 1,1 с | 8 | Норма для страницы без проекта. |

Общая гипотеза для всех страниц проекта: `requireProjectContext` и `requireUser` не кешируются на один запрос. Layout и страница загружают вход, проект и роль каждый сам.

Что это значит для людей: на Vercel база ближе, там цифры другие и не замерялись. При переезде на VPS важно, насколько база близко к сайту.
