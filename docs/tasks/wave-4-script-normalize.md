14. **Однотипные символы:** латиница внутри кириллицы (`MAMA` латиницей), `11a` → `11А`.

# ЧАСТЬ 1. ИНСТРУКЦИЯ

## Что получится

- Сценарий .docx в любом виде (со стилями английскими или русскими, без стилей, по отступам) при импорте приводится к одному стандарту: сцены, шапки, персонажи, реплики, ремарки, переходы.
- Без ИИ: правила плюс экран проверки, который показывает только то, в чём система не уверена.
- Словарь проекта запоминает ответы — и «да», и «нет». При новой версии те же вопросы не повторяются.
- Новая версия сценария в проекте с КПП и отчётами ничего не ломает: сцены не удаляются, существующие персонажи и локации не сливаются.
- Хронометраж новых сцен считается по нормализованному тексту.
- Сцена, которой нет в новой версии, по одному клику становится «вырезанной»: остаётся в истории, КПП и отчётах, но скрыта в либретто, не попадает в новые дни КПП и в хронометраж. Её можно вернуть.
- Титульная страница (название, автор, версия, дата, город) сохраняется в версию сценария.

## Конвейер

```
файл → разбор docx → типы блоков → нормализация → экран проверки → запись
                                        ↑                              │
                                 словарь проекта ←── решения (только при записи)
```

Нормализация — общий слой после разбора, чистые функции без обращений к базе (кроме чтения словаря и существующих имён проекта до них). Так её можно тестировать на файлах.

### Передача данных и лимиты

- Файл ≤ 3,5 МБ (проверка в браузере и на сервере, понятный текст отказа). Распакованный docx ≤ 30 МБ, число файлов в архиве ограничено, `document.xml` ≤ 20 МБ — защита от zip-бомбы (пункт 20 аудита, если не закрыт). Только .docx: проверка по содержимому, не по расширению.
- Тело запроса серверного действия ≤ 4 МБ (`next.config.ts`), у Vercel потолок 4,5 МБ на запрос **и на ответ**. Ответ предпросмотра — компактный: блоки нормализованного текста, вопросы, сводка. Замерь размер ответа на самом большом файле, запиши в отчёт.
- «Было → стало» по сцене считается в браузере из уже полученных данных, а не отдельным ответом сервера.
- Предпросмотр без состояния на сервере: никаких временных таблиц и черновиков. При «Импортировать» сервер не доверяет результату из браузера: либо повторно разбирает тот же файл и применяет решения (проверка хэша файла с предпросмотра), либо строго проверяет присланные блоки (типы из списка, длины, только текст). Что выбрать — предложи в шаге 0.

### 1. Определение типов блоков — три уровня

**Уровень 1. Стили Word.** Словарь названий стилей (без учёта регистра, по названию и по id стиля):
- английские: SCENE HEADING, ACTION, CHARACTER, DIALOGUE, PARENTHETICAL, TRANSITION, SHOT, GENERAL;
- русские: «Заголовок сцены», «Описание действия», «Имя героя», «Реплика», «Ремарка», «Переход», «Персонажи» (служебная строка со списком персонажей сцены).
Словарь расширяемый (константа в коде).

**Уровень 2. Отступы.** Если стилей нет (всё в «Обычном»), собрать частоты левых отступов абзацев и найти профиль. Пример из `moya-malenkaya-draft.docx`: имя персонажа ≈ 5,6 см, ремарка ≈ 4,1 см, реплика ≈ 2,5 см, действие — без отступа. Шапка сцены — жирный абзац без отступа с ИНТ/НАТ. Профиль ищется по файлу, а не задаётся числами. Учитывать отступ из стиля абзаца, если в самом абзаце его нет.

**Уровень 3. Текст.** Если нет ни стилей, ни отступов: шапка — строка с ИНТ/НАТ (любой регистр, с номером или без); персонаж — короткая строка в верхнем регистре (с расширениями в скобках) перед репликой; ремарка — текст в скобках; переход — CUT TO:, FADE TO BLACK, СМЕНА КАДРА, ЗТМ и т. п.; остальное — действие.

Уровни проверяют друг друга: стиль говорит «персонаж», а текст похож на шапку — вопрос на экран проверки.

### 2. Нормализация

**Символы (до всего остального).** Неразрывные и двойные пробелы, хвостовые пробелы, разные тире → одно. Латинские буквы-двойники внутри кириллического слова (`MAMA`, `КВАPТИРА`) → кириллица. Буква в номере сцены: `11a`, `11A` → `11А`. Ё = Е при сравнении, в отображении — как в файле у первого появления.

**Титульная страница.** Всё до первой шапки сцены, отцентрированное или с большими отступами, — метаданные: название, автор, версия, дата (как текст, не разбирать в тип даты), город, прочие строки. Показать на экране проверки (поля можно поправить руками), сохранить в версию сценария — одно поле с JSON из текстовых полей (миграция). Показать титульную на странице версии сценария. Почты и телефоны с титульной — не в журнал аудита.

**Шапка сцены** → номер · ИНТ/НАТ · объект · подобъекты · режим · пометка.
- Номер: `1.`, `1`, `Сц. 1`, `СЦЕНА 1`, с буквой (`11А`). Сцен без номеров — вопрос «пронумеровать подряд».
- ИНТ/НАТ: ИНТ, ИНТ., ИНТЕРЬЕР, INT, INT., НАТ, НАТ., НАТУРА, EXT, а также ИНТ/НАТ, НАТ/ИНТ, ИНТ-НАТ. Без учёта регистра.
- Объект и подобъекты: разделители `.` (с пробелом и без) и `/`. `ДОМ. ДЕТСКАЯ` → объект «ДОМ», подобъект «ДЕТСКАЯ»; `Квартира/спальня` → «КВАРТИРА» / «СПАЛЬНЯ». Точка внутри названия с латиницей или цифрами (`DDCT.КАБИНЕТ`) — тоже разделитель, но это проверяется тестом.
- Несколько мест в одной сцене: ` / ` между подобъектами (`ДОМ. ДЕТСКАЯ / КОРИДОР`) и `///` (`Квартира/спальня///коридор`) → несколько подобъектов одного объекта. Связь сцены с несколькими локациями в модели уже есть — использовать её. Если после ` / ` идёт другой объект — вопрос.
- Режим: после ` — `, ` – `, ` - ` или последним словом строки. Словарь: УТРО, ДЕНЬ, ВЕЧЕР, НОЧЬ, РАССВЕТ, ЗАКАТ, СУМЕРКИ, РЕЖИМ (расширяемый). Пометки: ПОЗЖЕ, НЕМНОГО ПОЗЖЕ, СЛЕДУЮЩЕЕ УТРО, ПРОДОЛЖЕНИЕ, (ПОЗЖЕ) — сохраняются как пометка. Пометка вместо режима («— ПОЗЖЕ») → режим предыдущей сцены, вопрос.
- Объект, подобъект, режим — в верхнем регистре.
- Шапка без ИНТ/НАТ (`1. ЗАКАДРОВЫЙ ГОЛОС`) — вопрос: сцена или пометка.
- Пустые шапки и шапки из одного номера (`37.`) — выбросить, сказать на экране проверки.

**Персонажи.**
- Расширения в скобках не создают персонажа: (З.К.), (ЗК), (З/К), (ВПЗ), (ПРОД.), (ПРОД), (V.O.), (O.S.), (CONT'D), (за кадром), в том числе вплотную: `ВИКТОРИЯ(ЗК)`. Расширение сохраняется у реплики.
- Верхний регистр, Ё = Е при сравнении, лишние пробелы.
- `(ДАЛЬШЕ)` и похожее отдельной строкой-«именем» — пометка продолжения, не персонаж.
- Цифра в конце (`СТАЖЕР1`) — вопрос: «СТАЖЕР 1» или опечатка «СТАЖЕР».
- Число в скобках после имени в действии (`ВИКТОРИЯ(27)`, `АННА (5)`) — возраст: не часть имени, не расширение, нового персонажа не создаёт. Возраст не сохраняется (решение владельца).
- Строка «Персонажи» под шапкой — список персонажей сцены. Сверить с говорящими; расхождения — вопрос. Персонаж только из этой строки (не говорит) — тоже персонаж сцены.
- Пустые абзацы со стилем персонажа — выбросить.

**Реплики и ремарки.** Несколько абзацев реплики подряд — одна реплика. Ремарка может стоять внутри реплики. Ремарка без персонажа перед ней (`(пауза)` после реплики) — продолжение реплики предыдущего персонажа.

**Переходы.** CUT TO:, FADE TO BLACK, FADE OUT, СМЕНА КАДРА, ЗТМ, ВЫХОД ИЗ ЗТМ — тип «переход».

**Текст в базу — только текст.** Никакого HTML и разметки из docx (пункт 4 аудита). Жирный и курсив из исходника теряются — так и задумано; если блоки сценария в базе хранят форматирование, скажи в шаге 0.

### 3. Похожие имена — предложения объединить

Для персонажей и локаций: совпадение после нормализации; расстояние редактирования ≤ 2 при длине ≥ 5; одно — начало другого («МАША» / «МАША ПЕТРОВА»); совпадение с уже существующими в проекте.

- Это только предложения. Расстояние ≤ 2 даёт ложные пары (МАРИЯ / МАРИНА) — поэтому они не входят в «Принять все».
- Сравнение с существующими в проекте: результат — «привязать к существующей записи» или «создать новую». **Существующие записи между собой не сливаются** (у них актёры, кастинг, разведка, КПП, статьи сметы) — это вне волны.

### 4. Новая версия в проекте с данными

- Импорт в проект, где уже есть сценарий, — новая версия сценария через существующий механизм версий; либретто обновляется существующей синхронизацией.
- Сцены новой версии сопоставляются с существующими: по нормализованному номеру, затем по шапке. Экран показывает: совпала без изменений · совпала, шапка изменилась (было → стало) · новая · **нет в новой версии**.
- Сцены, персонажи, локации **не удаляются** при импорте.
- Сцена, которой нет в новой версии, — вопрос «Пометить вырезанной?» с тем, где она используется (дни КПП, отчёты). Ответ «да» — статус «вырезана» (раздел 5), «нет» — сцена остаётся как есть. Для этой группы «Принять все» можно: действие обратимое.
- Вырезанная сцена снова есть в новой версии (тот же номер или та же шапка) — вопрос «Вернуть?».
- Ссылки КПП, `SceneShootAttempt`, отчётов и начислений на совпавшие и на вырезанные сцены сохраняются. Проверить на проекте «ТЕСТ импорт» с парой дней КПП.
- Номера существующих сцен импорт не перенумеровывает. Номер вырезанной сцены остаётся за ней. Если номер из файла занят другой сценой (в том числе вырезанной) — вопрос.

### 5. Статус «вырезана»

- Модель: у сцены поле «вырезана» — дата (`cutAt`, пусто — не вырезана). Не новое значение перечисления статусов. Кто вырезал — в журнале аудита.
- Либретто: вырезанные скрыты по умолчанию; фильтр «Показать вырезанные» — серые, номер зачёркнут. Действия «Вырезать сцену» (с `useConfirm`, в вопросе — где сцена используется) и «Вернуть». Право — правка либретто, проверка на сервере. Запись в аудит на каждое действие.
- КПП: вырезанную сцену нельзя добавить в день (проверка на сервере, не только в списке выбора). Если она уже стоит в дне — не убирается сама, а помечается «вырезана» в дне, решение за пользователем.
- Отчёты смен, `SceneShootAttempt`, начисления — не меняются: это история и факт.
- Хронометраж: итоги сценария и либретто без вырезанных сцен.
- Выгрузки либретто и КПП: вырезанные не попадают в выгрузку либретто по умолчанию, в КПП — с пометкой. Через общий конструктор колонок, своих выгрузок не делать.
- «Обзор»: число сцен — без вырезанных.
- Вызывной (волна 3) ещё не сделан — ничего не трогать, только записать в отчёт, что ему нужно учитывать статус.
- Синхронизация сценарий → либретто не должна снимать и ставить статус сама: только по ответу на экране импорта или кнопкой в либретто.

### 6. Экран проверки

- Группы: Титульная страница · Сцены (нумерация, шапки, сопоставление с прошлой версией) · Персонажи · Локации · Нераспознанные блоки.
- Каждый вопрос — один клик: принять, отклонить, выбрать из существующих.
- «Принять все» в группе — только для однозначных правок (регистр, пробелы, расширения, ё/е, латиница). Объединение похожих имён и нумерация — по одному.
- «Было → стало» для любой сцены.
- Ничего не пишется в базу до «Импортировать». Уход со страницы с ответами — предупреждение (`useFormGuard`).
- Без права правки сценария экран не открывается, действие отвечает отказом.

### 7. Запись

- «Импортировать»: сценарий, сцены, персонажи, локации и **решения в словарь** — в одной транзакции. Поиск и создание — пачками (`createMany`, выборка по списку имён), не запросом на строку (раздел 6 аудита). На тестовой базе запрос стоит 0,3–0,6 с — посчитай запросы на самом большом файле и замерь время. Упирается в таймаут транзакции — покажи цифры и варианты, сам не решай.
- Двойное нажатие и вторая вкладка не создают вторую версию: кнопка блокируется, сервер проверяет, что версия сценария не изменилась с момента предпросмотра.
- Аудит: одна запись «Импорт сценария» на импорт через `auditMutation` — файл (имя, размер), версия, сколько сцен/персонажей/локаций создано и привязано, сколько решений в словарь. Без текста сценария, почт и телефонов.

### 8. Словарь проекта

- Хранит решения в обе стороны: «МАРИЯ → персонаж #id», «КВ. ИВАНА → локация #id», «ЗАКАДРОВЫЙ ГОЛОС — не сцена», и отказы «МАРИЯ ≠ МАРИНА», «ДВОР ДОМА — отдельный объект».
- Цель — id существующей записи, если она есть; переименование персонажа правило не ломает. Цель удалена — правило не применяется и показывается на экране словаря как устаревшее.
- Тип правила — строка (константы в коде), не перечисление в базе: новые типы без миграции.
- Применяется молча при следующих импортах. Экран проверки показывает только новое и строку «применено правил словаря: N» с раскрытием.
- Экран словаря — в разделе сценария, пункт меню через `NavAccess`: смотреть — с правом просмотра сценария, удалять — с правом правки. Удаление — `useConfirm`, запись в аудит. Открытие экрана ничего не пишет.

### 9. Хронометраж

- По нормализованным блокам, формулой, которая уже есть в проекте (55 строк на страницу). Формулу не менять.
- В предпросмотре — итог по сценам и общий.
- Хронометраж уже существующих сцен, которые не менялись, не пересчитывать. Итоги — без вырезанных сцен.
