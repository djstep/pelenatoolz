- Страница импорта открывалась с правом просмотра сценария; действия проверяли право правки.
- docx разбирался на сервере дважды: текст (`mammoth` + регулярное выражение) и блоки (свой разбор `document.xml`). Стили Word не читались, тип блока угадывался по тексту, жирности, курсиву и отступу. Распаковка без лимитов (пункт 20 аудита не закрыт).
- Предпросмотр писал в базу: `ScriptImportJob` с JSON всего предпросмотра.

Сцены, персонажи, локации импорт не создавал; это делала отдельная панель «Синхронизация с либретто» (`applyScenesFromPreview`: по запросу на строку, без транзакции, у сцены оставляла одну локацию и заново ставила персонажей).
- Хронометраж — `Scene.planSeconds`, режим проекта (по словам / 55 строк на страницу / из файла / вручную); у мастера импорта была своя формула 1500 знаков на страницу.
- Пункт 4 аудита не закрыт: редактор вставляет `contentHtml ?? content` через `innerHTML`.
- Прогон текущим кодом: ddct — 35 сцен вместо 36, ни одного персонажа по стилям; draft — персонажи из титульной («МОЯ МАЛЕНЬКАЯ», «22.10.2026»); v4 — все шапки без номера получают номер «1».

## Решения владельца

1. **Режим.** Шапка в тексте сценария — как в файле после нормализации, импорт не пересобирает её через `buildSlugline`. В либретто — ближайшее из 4 значений: УТРО → РАССВЕТ (DAWN), ВЕЧЕР / СУМЕРКИ / РЕЖИМ → ЗАКАТ (DUSK). Новые значения режима — отдельной волной (в отчёт).
2. **Пометка** (ПОЗЖЕ и т. п.) — только в тексте шапки, без нового поля.
3. **«СЛЕДУЮЩЕЕ УТРО»** → режим УТРО + пометка, без вопроса. «Предыдущая сцена» — предыдущая шапка в файле. Для вопросов «режим взят у предыдущей сцены» «Принять все» разрешено.
4. **Шапка без ИНТ/НАТ и служебные слова.** Вопрос «сцена или пометка» — и для шапки без ИНТ/НАТ, и для шапки, где объект — служебное слово (словарь: ЗАКАДРОВЫЙ ГОЛОС, ТИТР, ТИТРЫ). «Не сцена» → блок «Примечание», текст после него — обычные блоки на своём месте, в титульную не уходит. Титульная — только то, что до первой шапки (включая шапку-примечание).
5. **Похожие локации — новое правило:** слово одного имени совпадает со словом другого с окончанием до 2 букв (ДОМ / ДОМА). Пары по одному, ответ «нет» запоминается словарём.
6. **Строка «Персонажи».** Вопрос только «говорит, но нет в строке». Молчащие из строки добавляются в сцену без вопроса. Сцена без строки не сверяется.
7. **Примечания.** Абзац с префиксом из словаря (РЕЖИССЕРСКАЯ ПОМЕТКА, ПРИМЕЧАНИЕ, NOTE; с двоеточием) — блок «Примечание», не действие (не экранное время).
8. **Переходы.** Только целая строка из списка (CUT TO, FADE TO BLACK, FADE OUT, СМЕНА КАДРА, ЗТМ, ВЫХОД ИЗ ЗТМ, ЗАТЕМНЕНИЕ), точка или двоеточие в конце допускаются. «Переход через коридор…» — действие.
9. **Хронометраж** — по режиму проекта той же функцией, что синхронизация (`estimateSceneTiming`). Выбор метода и формула «1500 знаков» из мастера убираются.
10. **Форматы.** На экране только .docx, сервер другие отклоняет. Код других форматов (kitsp, fdx, fountain, celtx, txt) удалить в шаге 7, список удалённого — в отчёт.
11. **Пункт 4 аудита — минимум в шаге 7:** редактор вставляет текст как текст, импорт никогда не пишет `contentHtml`. Полная очистка `contentHtml` — отдельной задачей до реальных пользователей (в отчёт как приоритет).
12. **Связи у совпавших сцен.** Ручную работу в либретто не стирать. Новые связи с персонажами и локациями — добавлять; связи, которых нет в новой версии, — вопрос «убрать связь?» («Принять все» для группы можно). Без ответа связь остаётся. Режим и ИНТ/НАТ — обновлять, показывать в «было → стало».
13. **Одна точка записи.** Одна общая функция для импорта и панели «Синхронизация с либретто»: пачками, в транзакции, с несколькими локациями, по правилу пункта 12. Пять неиспользуемых функций в `src/features/screenplay/lib/sync.ts` удалить (`syncAllScenesFromBlocks`, `ensureScenesFromBlocks`, `syncSceneFromSlugline`, `syncSceneCharactersFromBlocks`, `syncSceneScriptContent`), список — в отчёт. Панель владелец проверяет руками.
14. **`ScriptImportJob`** — не писать, таблицу и записи не трогать.
15. **Страница импорта** без права правки сценария не открывается.
16. **Групповое удаление сцен** (каскад на КПП и отчёты) — не трогать, в отчёт как риск.
17. Раздел «Уроки» в отчёте волны 2 не нужен — правила уже в ТЗ.

## Технические решения шага 0

- **Передача данных:** повторный разбор на сервере. Предпросмотр ничего не пишет, возвращает компактные блоки, вопросы, хэш файла и id текущей версии сценария. «Импортировать» присылает тот же файл, ответы, хэш и id версии; сервер сверяет хэш, разбирает файл заново, применяет ответы. Текущая версия сменилась — отказ (двойное нажатие, вторая вкладка).
- **Модель:** шаг 3 — таблица словаря (тип правила — строка); шаг 5 — `Scene.cutAt DateTime?` и `ScriptVersion.titlePage Json?` одной миграцией.
- **Локации:** пара «объект + подобъект» = `Location.name` + `Location.sublocation`; несколько мест в сцене — несколько `SceneLocation`.
- **Автотесты:** `node --import tsx --test` (без новых пакетов), скрипт `npm test`.
- **Распаковка docx:** своя, по центральному каталогу архива, через `zlib` с лимитами; `mammoth` для docx не нужен.

## Вопросы экрана проверки: постоянные и разовые (решение владельца 30.10.2026, шаг 2)

У каждого вопроса есть признак `persistent`.

- **Постоянные** — про содержимое; ответ пойдёт в словарь проекта (шаг 3) и применится при следующих импортах. Код — `тип:ключ`, ключ только из содержимого, без номеров сцен и позиций (`персонаж:СТАЖЕР1`, `шапка-не-сцена:ЗАКАДРОВЫЙ ГОЛОС`, `объекты:ДВОР ДОМА / ОПУШКА ЛЕСА`). Виды: склейка имён и локаций (шаг 3), «шапка не сцена», слово целиком латиницей, имя с цифрой, «два объекта».
- **Разовые** — только этот импорт, в словарь не попадают. Задаются по каждой сцене отдельно, код включает сцену: `тип:сцена:ключ` (`режим-не-указан:2:ИНТ. КОМНАТА`). Виды: режим не указан, режим от предыдущей сцены, нумерация, повтор номера, сцена без номера среди пронумерованных, сверка строки «Персонажи».
- **Сцена в коде разового вопроса** — номер из файла (текстом или автонумерацией Word), до ответов, чтобы код не менялся от ответа на соседний вопрос. Без номера — `п<порядок>`, при повторе номера — `5#2`.
- «Режим не указан» — по вопросу на сцену; «Принять все» в группе ставит одно выбранное значение во все сцены группы.

Решения агента, ждут подтверждения владельца:
- «Латиница внутри слова» (`КВАPТИРА`) — постоянный: ответ про слово, не про сцену.
- «Пронумеровать подряд» (ни у одной сцены нет номера) — один вопрос на файл (`нумерация:подряд`), не по сценам.
- «Тип блока» (расхождение уровней шага 1) — разовый; код по тексту абзаца, без сцены.

### Обязательно для шага 6 (запись): что сервер принимает от браузера

3. **Только исходные данные.** Сервер при импорте не принимает от браузера ни блоки, ни вопросы, ни сводку — только файл, ответы (по кодам вопросов), правки титульной, хэш и id версии. Сам разбирает файл заново и применяет ответы той же функцией, проверяет хэш и текущую версию, проверяет, что все обязательные вопросы (`required`) отвечены; неизвестные коды ответов игнорирует.
4. **Открытие страницы версий ничего не пишет.** Страница версий сценария (`/screenplay`) при открытии не создаёт версию и блоки (сейчас — `ensureCurrentScriptVersion` + `bootstrapScriptBlocks`). Первая версия создаётся только действием с правом правки сценария (проверка на сервере). *Решение владельца 30.10.2026, после шага 4.*

### Обязательно для шага 7: облегчённый docx (решение владельца 30.10.2026, после шага 4)

1. Браузер отправляет на сервер не исходный файл, а облегчённый docx — только текстовые части, которые читает разбор (`[Content_Types].xml`, `word/document.xml`, `word/styles.xml`, `word/numbering.xml`); картинки и прочее не отправляются.
2. Исходный файл — до 50 МБ (проверка в браузере, понятный текст отказа).
3. Лимит 3,5 МБ — на отправляемое (облегчённый docx), проверка в браузере и на сервере. Лимиты распаковки на сервере (30 МБ, число файлов, `document.xml` ≤ 20 МБ) остаются.
4. Хэш файла для сверки предпросмотра и «Импортировать» — от отправляемого облегчённого docx (сервер видит только его). *Техническое следствие, дописано агентом.*

#### Для отчёта

- **В ключ шапки входит режим** (и пометка): «ИНТ. КУХНЯ — ДЕНЬ» и «ИНТ. КУХНЯ — НОЧЬ» — разные ключи.

  - Смена режима вместе со сдвигом номеров: эта сцена не находится ни через версию, ни по проекту — новая сцена с вопросом «номер занят» плюс старая с вопросом «вырезать?». Пара видна на экране, не тихая. *Владелец: вернуться после реальных импортов.*

### Как устроена синхронизация

- Источник — блоки версии (`typingFromVersionBlocks`): тип блока как в версии, без угадывания (вопросов «тип абзаца» нет), титр — действие, «непечатный текст», группы и папки не читаются. Нормализация и план записи — те же, что у импорта (`normalizeScript` с `sync: true`, `planImport`), сопоставление сцен — через шапки этой же версии, затем по проекту.
- Запись — та же `writeScript`, режим «существующая версия»: новая версия не создаётся, текст и титульная не меняются, у блоков обновляется только сцена (один SQL-запрос на пачку); версия становится текущей. Блок, которого нет в нормализации («(ДАЛЬШЕ)», пустой), получает сцену предыдущего; до первой шапки — без сцены.
- Защита: блокировка проекта и сверка хэша блоков версии (id, тип, текст, сцена) с предпросмотра — изменились (правка версии, вторая вкладка, повторное нажатие) — отказ.
- Журнал: одна запись «Либретто обновлено из версии N: сцен создано X, привязано Y» (счётчики, без текста).
- Предпросмотр синхронизации — серверная загрузка страницы, только чтение.
