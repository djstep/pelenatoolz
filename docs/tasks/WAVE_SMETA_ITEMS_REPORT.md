## Модель

- **Строка сметы = прежняя `BudgetItem`** с теми же id: начисления, платежи, статьи по умолчанию у актёров и ресурсов, отчёт смены, план/факт и строки версий ссылаются на неё как раньше. Строка нового формата — с подстатьёй (`subarticleId`) и номером; запись без подстатьи — старая табличная смета.
- **Уровни:** статья шаблона фильма (`BudgetTemplateArticle`, номер не переиспользуется) → статья цеха (`BudgetArticle`) → подстатья (`BudgetSubarticle`) → строка. Код строки `TR-05.02.03` собирается из префикса цеха и номеров уровней (счётчики, номера не переиспользуются); на экране кодов нет нигде, в Excel — колонка «Код».
- **Строка:** наименование, тип расхода, единица, количество, ставка, до трёх множителей (переменная проекта или своё число), форма оплаты, налог % (копия процента формы, правится), архив.
- **Справочники проекта:** типы расходов (10), формы оплаты с процентом по умолчанию (самозанятый 6, ИП 6, ГПХ / наличные / юрлицо — пусто), сопоставление «тип контрагента → форма оплаты» (только ИП и самозанятый), резерв и агентские % на проект.
- **Переменные:** СМЕНЫ, СЕРИИ (пусто — из параметров проекта), ДНИ ПОДГОТОВКИ, НЕДЕЛИ (пустые) и свои.
- **Версия сметы:** `format` SHEET (старый лист, только чтение) или ITEMS — снимок (статьи, подстатьи, строки с расчётом, значения переменных на момент утверждения) и строки плана `BudgetVersionLine` для плана/факта. Пометка `recalcByVariables` — версия «пересчёт по переменным».

## Права

- Глава цеха правит смету своего цеха (статьи из шаблона, подстатьи, строки, импорт, отправка).
- Продюсер утверждает и возвращает, ведёт шаблон статей и сводную, утверждает пересчёт по переменным; продюсер, который сам глава цеха, тоже правит — в версии это отмечается.
- Роль «Сметы — просмотр всех» только читает (сводную видит, выгружать на Диск не может).
- Переменные, типы расходов, формы оплаты, сопоставление, резерв и агентские меняют продюсер и «Финансы: правка»; главы видят переменные и формы оплаты в смете цеха только для чтения.
- Во всех действиях: вход, id из браузера — `isId` и `assertInProject` до первой записи, `projectId` только из контекста; ошибка «чужой объект» — `isNotInProjectError`. Подделанные запросы проверены в e2e (c31, c32, c33).
- Журнал: правки сметы, утверждение, возврат, пересчёт, импорт, справочники, переменные — `auditMutation` в той же транзакции.

## Расчёты

- Сумма = Кол-во × Ставка × множители; Налог = Сумма × Налог % / 100; Итого = Сумма + Налог. Decimal с точностью 40 знаков, округление до копеек на строке (половина вверх), итоги — суммы округлённых строк.
- Пустая переменная-множитель, нет количества или ставки — у строки нет суммы, пометка «не задана переменная: …», в итог не входит; такая смета не отправляется и не утверждается.
- Итоги в списке смет, сводной и на экране — пересчётом по действующим значениям переменных, а не из сохранённых сумм.
- Смена переменной или смен / серий проекта пересчитывает сохранённые суммы строк в той же транзакции (все сметы проекта под блокировкой); утверждённая версия не меняется; смета «утверждена» становится черновиком, при возврате значения — снова «утверждена»; «на утверждении» остаётся на утверждении (решение владельца); пометка «изменилась после утверждения» с перечнем переменных считается по версии.
- Утверждение сверяет отпечаток снимка (строки и значения переменных), который видел продюсер.
- Резерв и агентские — % от итога цехов с налогом (агентские — без резерва), отдельными строками, входят в план проекта.

## Следующий шаг: оценка

### Налог по форме оплаты в начислениях и платежах

Сейчас у начисления и платежа свой налог % вручную (`Accrual.taxPercent`, `CashPayment.taxPercent`), строка сметы — по `budgetItemId`, договор — по `contractId`.

Предложение:
- поле «Форма оплаты» у начисления и платежа (необязательное, ссылка на справочник проекта; миграция — один nullable внешний ключ на таблицу);
- налог % по умолчанию: форма строки сметы → иначе форма по типу контрагента (сопоставление шага 3) → иначе пусто; процент можно поменять, как в смете;
- выбор строки сметы в начислении подставляет её форму и налог;
- отчёты и план/факт уже считают «с налогом» — менять не нужно; нужна проверка, что факт по строке сравнивается с планом строки с тем же налогом.

Объём: одна миграция, правка двух форм и двух действий, e2e. Около одного шага волны. Риск — старые начисления без формы: оставить как есть, форма только для новых.

### Связь «договор ↔ строка сметы»

Сейчас договор связан с контрагентом, начисления — и с договором, и со строкой сметы, но сам договор со строкой не связан.

Предложение:
- связь «многие ко многим» `ContractBudgetItem` (договор может закрывать несколько строк, строку — несколько договоров) с суммой распределения;
- в форме договора — выбор строк сметы своего цеха (готовый выбор строк из начислений), проверка `assertInProject` и что строки из смет, которые видит автор;
- план/факт: колонка «Законтрактовано» между планом и начислено, предупреждение «договоры больше плана строки»;
- налог договора по умолчанию — из формы строки, если она одна.

Объём: миграция, форма договора, план/факт (экран и Excel), права и e2e. Около двух шагов. Вопрос владельцу: распределять сумму договора по строкам вручную или достаточно отметки «к каким строкам относится».

**Решение владельца (10.11.2026):** только отметка, к каким строкам относится договор, без ручного распределения сумм — суммы через начисления. Отложено в бэклог (`docs/tasks/BACKLOG.md`); старый код основного листа — тоже в бэклог.
