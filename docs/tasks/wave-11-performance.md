# ЧАСТЬ 1. ИНСТРУКЦИЯ

## Что получится

Страницы открываются быстрее и меньше нагружают базу — при тех же функциях. Сначала замер, потом правки по списку, который ты утверждаешь, потом замер ещё раз с цифрами «было → стало».

## Что меряем и почему не миллисекунды

Сейчас база в Neon, доступ через VPN — время ответа на 80% будет временем VPN, а не кода. Поэтому меряем то, что от сети не зависит:
- **сколько запросов к базе** делает каждая страница и действие (лишние запросы — главная причина тормозов);
- **сколько кода скачивает браузер** на каждой странице;
- **сколько данных** приходит в браузер (лишние поля, весь журнал вместо страницы);
- Lighthouse локально на сборке (`next build && next start`) — для сравнения «до/после», не как абсолютная цифра.

Настоящие миллисекунды и серверная часть (кеш, пул соединений, сжатие, CDN) — после переезда на VPS, отдельным шагом.

## Подготовка

1. Все функциональные волны слиты.
2. Миграции возможны (индексы) — ветка базы dev/e2e.
3. В базе e2e — «тяжёлый» тестовый проект: 200+ сцен, 40 дней КПП, 50 человек команды, смета на 500 строк, журнал на 5 000 записей. Claude Code сделает генератор на шаге 0.
4. Файл в `docs/tasks/wave-11-performance.md`, коммит в `main`. Новая сессия Claude Code.

## Как идёт работа

| Шаг | Что | Как проверить руками |
|---|---|---|
| 0 | Генератор тяжёлого проекта, замер, список правок с ожидаемым эффектом | Утверждаешь список |
| 1 | База: лишние запросы, индексы, выборка нужных полей, страницы списков | Тяжёлый проект: либретто, КПП, журнал открываются |
| 2 | Браузер: ленивая загрузка тяжёлого (Univer, редактор, перетаскивание, экспорт), лишний клиентский код | Смета, сценарий, КПП работают как раньше |
| 3 | Тяжёлые списки: КПП, либретто, журнал | Прокрутка на 200+ сценах плавная |
| 4 | Повторный замер, отчёт | Таблица «было → стало» |

- Новые пакеты.

## Правила волны

- Поведение, функции, тексты, права не меняются. Каждая правка — с цифрой «было → стало» по метрике из шага 0. Правка без измеримого эффекта — не делать.
- База находится за VPN: время ответа не метрика. Метрики: число запросов к базе на страницу/действие, объём данных из базы, размер JS на маршрут (`next build`), Lighthouse локально на `next start` (только для сравнения до/после).
- Права: оптимизация не должна обходить проверки прав (кеш, общий для пользователей с разными правами, — запрещён; выборка «всё, потом фильтр на клиенте» — запрещена).
- Миграции (индексы) — только на ветках dev и e2e. На прод не применять.
- Не делать инфраструктурного: кеш на Redis, CDN, пулы, сжатие — это после VPS. В отчёт — список таких идей.
- Новые пакеты — только после моего «да» (кандидат на анализ размера: `@next/bundle-analyzer`, только как dev-зависимость).

## Шаг 0. Замер

1. Генератор тяжёлого проекта для базы e2e (скрипт в `scripts/` или `e2e/`): 200+ сцен с персонажами и локациями, 40 дней КПП со сценами, 50 человек команды, 30 договоров, смета цеха на 500 строк, сводная, 5 000 записей журнала, 100 событий календаря. Запускается одной командой, повторный запуск не дублирует.
2. Подсчёт запросов: включи логирование запросов ORM на время замера (не в коммит, или под флагом окружения). Для ключевых страниц и действий: обзор, либретто, карточка сцены, КПП, перетаскивание сцены, вызывной (правка), смета цеха, сводная, начисления, журнал, команда, календарь — число запросов, есть ли повторяющиеся (N+1), объём строк.
3. Размер JS на маршрут из вывода `next build`, топ-10 тяжёлых, что их утяжеляет (анализатор — после «да»).
4. Lighthouse локально на `next start` для 6 страниц (desktop и mobile), сохранить отчёты в `docs/tasks/ref/perf/before/`.
5. Индексы: внешние ключи и поля фильтров/сортировки, по которым нет индекса.
6. Список правок: проблема → где → метрика сейчас → ожидаемо после → риск → нужно ли моё «да» (меняет ли поведение). Отсортировать по эффекту.

Жди утверждения списка и «дальше».

## Шаг 1. База

Только утверждённое: повторяющиеся запросы → один запрос с нужными связями или пакетная выборка; выбирать только нужные поля; индексы; длинные списки (журнал, операции) — постранично на сервере, если сейчас грузится всё (если меняет вид — по «да»); тяжёлые подсчёты — одним агрегирующим запросом.

## Шаг 2. Браузер

Только утверждённое: ленивая загрузка тяжёлых библиотек (Univer, редактор сценария, перетаскивание, экспорт в Excel, сравнение версий) там, где они не нужны с первой отрисовки; перенос в серверные компоненты того, что не требует интерактивности; лишние повторные отрисовки на КПП и в либретто (измерить React Profiler'ом, не на глаз).

## Шаг 3. Тяжёлые списки

КПП с 40 днями, либретто с 200+ сценами, журнал: если прокрутка тормозит по замеру — виртуализация списка (пакет — после «да») или мемоизация. Перетаскивание, выделение, фильтры, печать, экспорт — работают как раньше, проверить e2e.

## Шаг 4. Повторный замер и отчёт

1. Те же замеры, что в шаге 0, на том же тяжёлом проекте; Lighthouse — в `docs/tasks/ref/perf/after/`.
2. `docs/tasks/WAVE_11_REPORT.md`: таблица «страница/действие — запросов было → стало — JS было → стало — Lighthouse было → стало»; миграции (индексы); что не сделано и почему; список инфраструктурного на после VPS (кеш, пул соединений, сжатие, CDN, реальные замеры времени).
3. Генератор тяжёлого проекта оставить в репозитории (пригодится после VPS).
4. Не пушить и не сливать в `main`.
