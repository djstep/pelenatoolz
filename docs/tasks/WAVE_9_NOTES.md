## Сдвиг даты пробы

Проверено 07.11.2026 на `2026-10-31` через ту же логику, что в `parseDateInput`.

| Где | Пояс процесса | Результат | В `@db.Date` уйдёт |
|---|---|---|---|
| Сервер, контейнер `app` | UTC, `TZ` не задан | `2026-10-31T00:00:00Z` | 31.10, верно |
| Компьютер разработки | Europe/Moscow | `2026-10-30T21:00:00Z` | 30.10, на день раньше |
| Компьютер, `TZ=UTC` | UTC | `2026-10-31T00:00:00Z` | 31.10, верно |

На проде сдвига нет. Сервер живёт по МСК, но контейнер по UTC, поэтому результат держится только на умолчании образа. Сдвиг есть на локальном сайте, в том числе на сайте для e2e: запись пробы через форму там встанет на день раньше.

В календаре `Audition.date` и `AuditionSchedule.date` читаются как есть (`toDateKey`). `ShootDay.date` — через пояс проекта, с запасом в день по краям диапазона: на компьютере это полночь по Москве, на сервере полночь UTC.

## Часовой пояс: UTC везде (решение владельца, коммит `869a9c9`)

- Прод: `TZ: UTC` у `app` и `migrate` в `docker-compose.prod.yml`. Поведение не меняется, но больше не держится на умолчании образа. `Europe/Moscow` ставить нельзя: появится сдвиг на день.
- Свой компьютер: `npm run dev`, `npm start`, `npm test` идут через `node --import ./scripts/tz-utc.mjs`. Пакетов не добавлялось.
- e2e: `process.env.TZ = "UTC"` в `playwright.config.ts` и `TZ` у сайта в `webServer.env`. Браузер тестов остаётся в поясе Москвы, как у людей.
- Проверка: в `c22` запись пробы на 31.10 через форму сохраняется как 31.10.

После перехода на UTC в e2e видно предупреждение React о расхождении текста на `/audit`: `audit-workspace.tsx` выводит время `toLocaleString` без пояса, и сервер в UTC и браузер в Москве пишут его по-разному. На проде так и было: сервер там всегда был в UTC. Не чинилось, это вне волны.

## Принято на шаге 1

- `typeId` у события: `NO ACTION`, а не `RESTRICT`, иначе удаление проекта упадёт. Проверено на базе e2e: проект с типом, событиями и участником удалился, строк не осталось.
- Типы из миграции получают id в формате uuid, новые — cuid. Проверять `typeId` на шаге 2 только как непустую строку, без `.cuid()`.
- Начальные типы не создаются при открытии страницы, чтобы чтение ничего не писало. Источники три: миграция, создание проекта, сид. Список в коде и миграции сверяет юнит-тест.
- Порядок типов перетаскиванием не делался: в ТЗ его нет. Новый тип встаёт в конец.

## Записано, не чинилось

- **Id из браузера без проверки типа.** `requireProjectContext` и `requireProjectAccess` не проверяют, что `projectId` — строка. Prisma примет объект-фильтр, например `{ not: "x" }`. Находка reviewer на шаге 1, запросом не воспроизводилась. В действиях календаря закрыто: проект берётся из `ctx.project.id`, `typeId` проверяется. Те же условия есть в других модулях, например `crew/actions.ts`. Надёжнее одна проверка в этих двух функциях, это отдельная задача.
- **Последний видимый тип.** Проверка без блокировки: два одновременных скрытия оставят ноль видимых типов. Обратимо кнопкой «Показать».
- **`pelena_dev` пуста:** пользователей нет, войти нельзя. Проверки шага 1 шли на базе e2e.

## Принято на шаге 2

- Адрес: `/preproduction/calendar?view=month|week|list&date=ГГГГ-ММ-ДД`. Неизвестный вид — месяц, мусор в дате — сегодня по поясу проекта, годы вне 2000–2100 не принимаются.
- На телефоне (до 767 px) без вида в адресе экран сам переходит на список. Ссылку с явным видом не трогает.
- Диапазон: месяц — полными неделями (сетка 6×7 или 5×7), неделя — с понедельника, список — ровно месяц, вперёд и назад на месяц.
- Ячейка месяца: до 3 событий и «ещё N». Щелчок по пустому дню — новое событие на весь день (при праве правки), по дню с событиями и по числу — неделя этого дня. Кнопка «+» в углу дня тоже создаёт событие.
- Неделя: строка «весь день» и сетка 00:00–24:00, открывается с 08:00 или с раннего события. Пересекающиеся события стоят рядом в полосах. Щелчок по часу — новое событие с этого часа.
- Список: дни с событиями, подряд пустые дни свёрнуты в одну строку «… событий нет» с кнопкой «+ Событие».
- Событие через полночь стоит в обоих днях, окончание ровно в 00:00 следующий день не занимает. Многодневное «весь день» стоит в каждом своём дне.
- Строка события в месяце и неделе: время и название первой строкой, тип словом второй. Полное описание — в подсказке и для чтения с экрана.
- Окно события: тип (скрытые не предлагаются, кроме уже назначенного), весь день или время, начало и окончание, объект из «Локаций» и место текстом, участники, цеха, заметка. Конец сам сдвигается, если начало ушло позже него. «Удалить» — с подтверждением. Несохранённые изменения — общий механизм окна.
- Без права правки окно показывает событие без полей.
- Выбор людей: команда — с `crew:read`, актёры и кандидаты — с `cast:read`, объект — с `script:read`. Чего не видно, сервер сохраняет как было. Кандидат, утверждённый на роль, кандидатом не предлагается: он уже актёр. Человек из архива команды в событии остаётся, но нового из архива добавить нельзя.
- Журнал события пишет название, тип, время, место и число участников и цехов, без имён: его читают все с просмотром календаря.
- `typeId` и прочие id проверяются как непустая строка и через `assertInProject`, проект — из `ctx.project.id`.

## Записано на шаге 2, не чинилось

- **Поле времени `HhMmInput` под нагрузкой.** После фокуса оно выделяет текст через `requestAnimationFrame`. Когда сайт разработки занят сборкой, кадр запаздывает и `select()` возвращает фокус в поле времени, пока ввод уже идёт в следующее поле: введённое туда пропадает. Человек так быстро поля не переключает. В `c25` ввод сделан щелчком и набором по клавише. Компонент общий, был до волны.
- **Скрытые кандидаты в e2e.** Нет тестового аккаунта без `cast:read`: проверка «+N кандидатов» и ответа сервера без имён будет на шаге 5 вместе с проверкой проб.
