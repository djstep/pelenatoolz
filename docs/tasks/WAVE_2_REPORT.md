# Волна 2 — отчёт: сметы цехов, утверждение, план/факт

ТЗ — `docs/tasks/wave-2-smeta.md`. Все решения, замеры и подробности проверок — `docs/tasks/WAVE_2_NOTES.md`. Ветка `feat/wave-2-smeta`, 24 коммита от `main`, в `main` не слито, не запушено.

## Коротко

- У каждого цеха своя смета (книга Univer) с основным листом по шаблону. Строки с кодом — статьи. Глава цеха правит смету своего цеха, продюсер видит все и утверждает или возвращает. «Сметы — просмотр всех» — только чтение.
- Утверждённая версия — неизменяемый снимок (защита и в коде, и триггерами в базе). План — последняя утверждённая версия.
- Начисления и платежи ссылаются на статьи смет. Отчёт смены сам создаёт начисления со статьёй по умолчанию актёра, ресурса или объекта.
- Экраны «План/факт» и «Сводная книга», выгрузки в Excel с защитой от формул.
- Вкладка «Статьи» (`budget`), шаблоны смет и таблица `Payment` удалены.
- Автосохранение сметы — только при изменении данных, только изменённые листы, без конфликтов между вкладками. Импорт Excel переведён на ExcelJS, пакет `xlsx` удалён.

## Модель данных (кратко)

- `Department` (цех): проект, название, префикс кодов (уникальны в проекте), порядок. `DepartmentHead` — главы (участники проекта).
- `Budget` (книга цеха, одна на цех): основной лист, статус `DRAFT / SUBMITTED / RETURNED / APPROVED`, поля отправки и возврата, `changedAfterSubmitAt`, `revision` (растёт при каждом сохранении). `BudgetSheet` + `BudgetSheetData` — листы (ключ листа уникален в книге).
- `BudgetItem` (статья): код уникален в проекте; текущие значения черновика; `archivedAt`, если код пропал с основного листа. Тот же код — та же статья.
- `BudgetVersion` + `BudgetVersionLine` — утверждённая версия: номер, кто и когда утвердил, итог, снимок основного листа; строки — ссылка на статью и копия значений. Изменить или удалить нельзя (триггеры), удаляется только вместе с проектом.
- `Accrual.budgetItemId`, `CashPaymentBreakdown.budgetItemId` — необязательная ссылка на статью (пусто — «без статьи»). У начисления из отчёта смены — `workRowId` + `reportPart` (смена / переработка / доплаты / км), `reportZeroedAt`, `editedManually`.
- Статьи по умолчанию: у `Actor` и `Location` — основная и переработка, у `ResourceItem` ещё км.
- `ProductionReportWorkRow.overtimeRates` — снимок почасовых ставок переработки в строке отчёта.
- Права: раздел матрицы `smeta_all` («Сметы — просмотр всех»). Раздел `budget` убран.

Тип записи «Выгрузка смет» (`smeta_export`), действие **CREATE**. В `AuditAction` нет значения «выгрузка», а новое значение перечисления требует миграции — ради журнала её не делали. В тексте записи — кто, что, цех, период, без сумм. Если нужен отдельный фильтр «выгрузки» в журнале — добавить `EXPORT` в `AuditAction` отдельной миграцией.

## «Обновить из КПП» — не в одной транзакции

Пересборка отчёта смены идёт несколькими шагами без общей транзакции: сцены, строки работы (`applyWorkRowSync`), начисления (`syncReportAccruals`), обнуление начислений убранных строк (`zeroAccrualsOfWorkRows`). На тестовой базе это 20+ запросов по ~1 с, и транзакция упиралась бы в таймаут.

Защита сейчас такая:
- уникальные ключи: строка = отчёт + источник, начисление = строка + часть;
- повторяемость: второй одновременный запрос получит «Отчёт сейчас обновляет кто-то ещё — обновите страницу и повторите», повторное обновление доводит дело до конца.

**Что вернуть при переезде на VPS:** `refreshProductionReport` — все шаги через один `tx` с блокировкой строки отчёта (`SELECT … FOR UPDATE`), как у сметы.

## Что сделать на Vercel при слиянии

**1. Миграции сами не применятся.** На Vercel сборка идёт скриптом `vercel-build` = `prisma generate && next build`, `migrate deploy` там нет. `vercel.json` и CI в проекте нет.
- Сейчас Vercel подключён к той же тестовой базе Neon, и в ней **все миграции волны уже применены**. Значит, при слиянии запускать ничего не нужно. Проверка: `npx prisma migrate status` → «Database schema is up to date!».
- Важно: раз база уже на новой схеме, сайт на Vercel со **старым** кодом из `main` работает с таблицами, которых больше нет: `BudgetLine`, `Payment`, старые книги без цеха. «Статьи», старая смета и отчёт смены там сейчас могут падать. Слияние это исправит — код и база снова совпадут.
- Когда у прода будет своя база: перед деплоем или сразу после — `npx prisma migrate status`, затем `npm run db:migrate` (`prisma migrate deploy`) с адресами базы прода. Миграции берут `DIRECT_URL`, если он задан. Или добавить `prisma migrate deploy` в `vercel-build` — решение за вами.
- Миграции волны необратимые: удаляют старые книги смет, шаблоны, `BudgetLine`, `Payment`. Перед применением к базе с настоящими данными — резервная копия.

**2. Убрать `pgbouncer=true` из `DATABASE_URL` на Vercel.**
- Vercel → проект → Settings → Environment Variables → `DATABASE_URL`: убрать `&pgbouncer=true`. Адрес с `-pooler` оставить. `DIRECT_URL` не трогать.
- Переменные действуют только на новые деплои — после правки нужен Redeploy.
- Что проверить после: открыть «Сметы», «План/факт», «Сводную книгу», отчёт смены; поправить ячейку сметы (сохраняется); отправить и утвердить смету; создать начисление и платёж. В Vercel → Logs поискать `prepared statement` (ошибки вида `prepared statement "s0" already exists / does not exist`).
- Будут такие ошибки — вернуть флаг и сделать Redeploy.
- Локально без флага ошибок не было; скорость: один запрос 1,57 → 0,3–0,6 с, «План/факт» 9,5 → 3 с.

**3. Лимит 4 МБ для серверных действий на Vercel проходит.** У Vercel потолок тела запроса к функции — 4,5 МБ. Лимит в `next.config.ts` — 4 МБ, браузер сам не отправляет больше 3,8 МБ, файл импорта — до 3,5 МБ. Запрос больше 4,5 МБ Vercel отклонил бы ещё до приложения (413).
- Проверено только локально. После деплоя стоит один раз сохранить на Vercel смету с листом больше 1 МБ.
- У Vercel тот же потолок 4,5 МБ и на **ответ** функции. Выгрузки Excel (План/факт, сводная книга) возвращаются в ответе действия в base64, а их предел в коде — 10 МБ. Файл больше ~3 МБ на Vercel не дойдёт. Сейчас файлы — килобайты. При переезде на VPS ограничения нет.

- Univer у основного листа (на нём защищённый диапазон) делает недоступным и «Переименовать лист».

## На переезд на VPS

- **«Обновить из КПП» / «Создать из КПП» — в одну транзакцию** с блокировкой строки отчёта: сцены, строки, начисления, обнуление — через один `tx` (см. раздел выше).
- **Меньше запросов при сохранении сметы** (сейчас ~20 на одно сохранение основного листа):
  - вход и права (~6): участник, роль, проект, главы цехов — читать одним запросом или кешировать на запрос (`cache()`);
  - `assertInProject` цеха и чтение сметы — объединить;
  - разбор: коды других цехов и факт по статьям — параллельно (сейчас последовательно);
  - в транзакции: запись листа (`update` + `upsert` данных) и `syncItems` (по запросу на изменённую статью) — пакетно;
  - запись в журнал и `listDepartmentCodes` — только при изменении статей (уже так).
  На VPS рядом с базой запрос стоит миллисекунды, так что это скорее про запас, чем про срочность.
- Выгрузки Excel можно отдавать файлом (маршрут), а не base64 в ответе действия — уйдёт и потолок ответа.
- Лимит тела серверного действия (сейчас 4 МБ под Vercel) можно поднять, если понадобятся листы больше 2,5 МБ.
