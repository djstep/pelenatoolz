## ЗАДАЧА 1. Облачный диск привязывается к чужому аккаунту

**Где:** `src/app/api/cloud/google/callback/route.ts` (около строки 59), аналогичный callback для Яндекса, а также маршруты `authorize` для обоих.

**Проблема:** после согласия в Google или Яндексе связь записывается на пользователя из подписанного параметра `state`, а не на того, кто сейчас вошёл. Злоумышленник отправляет жертве свою ссылку авторизации, жертва даёт согласие, и её диск привязывается к аккаунту злоумышленника.

**Сделать (для Google и Яндекса):**
1. Разберись, как формируется и подписывается `state` в `authorize`.
2. Добавь в `state` время выпуска. В callback отклоняй `state` старше 10 минут.
3. В callback получи текущую сессию через Auth.js. Нет сессии — отказ. id пользователя из сессии не совпадает с id из `state` — отказ, ничего не записывать.
4. При отказе делай редирект на ту же страницу, куда callback ведёт при ошибке сейчас, или возвращай ошибку так же, как текущий код при неудаче. Новых экранов не делай.

## ЗАДАЧА 2. Редирект на чужой сайт

**Где:** `src/features/auth/actions.ts` (около строки 72), `src/app/api/cloud/google/authorize/route.ts` (около строки 9) и все остальные места, где адрес возврата берётся из параметра запроса или формы (`callbackUrl`, `returnTo`, `next`, `redirect` и т.п.). Найди их поиском.

**Проблема:** адрес возврата проверяется слабо: `//чужой-сайт.ru` проходит, и после входа пользователя уводит на чужой сайт.

**Сделать:**
1. Создай `src/shared/lib/safe-redirect.ts` с функцией `safeRedirectPath(input: unknown, fallback: string): string`. Она возвращает `input` только если это строка, которая:
   - начинается ровно с одного `/`;
   - вторым символом не имеет `/` или `\`;
   - нигде не содержит `\` и управляющих символов;
   - не длиннее 2000 символов.
   Во всех остальных случаях возвращает `fallback`.
2. Используй её во всех найденных местах. Фолбэк — тот адрес, который там используется сейчас по умолчанию.
3. Если адрес возврата содержит префикс языка (`/ru/...`), проверь, что он продолжает работать.

## ЗАДАЧА 3. Известный ключ шифрования по умолчанию

**Где:** `src/features/cloud/lib/token-crypto.ts` (около строки 7).

**Проблема:** если секрет не задан, токены дисков шифруются известной строкой `dev-cloud-secret-change-me`. Кто получит дамп базы, сможет расшифровать доступ к дискам.

**Сделать:**
1. При `NODE_ENV === "production"` и пустом секрете — бросать понятную ошибку **в момент шифрования или расшифровки**, а не при импорте файла (иначе может упасть сборка, где секрета нет).
2. В разработке оставить фолбэк, но с `console.warn` один раз.
3. Секрет должен быть не короче 32 символов в production. Иначе — та же ошибка.
4. В отчёте **крупно** напиши точное имя переменной окружения, которую надо задать на хостинге.

## РОЛЬ И КОНТЕКСТ

Ты исправляешь уязвимость в мультипроектной SaaS-платформе для кинопроизводства. Стек: Next.js 16 (App Router, server actions), TypeScript, Prisma 6. Права в проекте задаются ролями; матрица прав хранится в базе (`src/features/roles/permissions-matrix.ts`), старые имена прав переводятся в матрицу в `src/features/memberships/permissions.ts`. Перед началом прочитай `docs/audit/FIX_REPORT_1.md` и `src/features/memberships/assert-in-project.ts`.

## ПРАВИЛА

1. Меняй только файлы из задачи и новые файлы, которые для неё нужны. Все изменённые файлы перечисли в отчёте.
2. Никакого рефакторинга, переименований и переформатирования.
3. Не меняй `prisma/schema.prisma`, не создавай миграции, не запускай команды Prisma, которые меняют базу.
4. Не меняй интерфейс. Новые тексты ошибок — короткие, по-русски, в стиле соседних.
5. Не ослабляй существующие проверки прав.
6. Не делай git commit и git push. Не пиши «остальное аналогично».

## ПРОБЛЕМА

`src/features/roles/actions.ts` (около строки 111) и `src/features/projects/actions.ts` (около строки 430). Кто имеет право управлять участниками, может переписать любую роль, включая свою и системную «Продюсер», и назначить себе любую роль. Координатор может сам выдать себе права продюсера и доступ к финансам.

## ЧТО СДЕЛАТЬ

Сначала найди все действия, которые:
- создают, меняют или удаляют роль и её права;
- меняют роль участника проекта;
- создают приглашение с ролью или принимают его;
- удаляют участника.

Затем во всех этих действиях введи правила. Каждое правило — **на сервере**, до записи:

1. **Системные роли.** Выясни по схеме, как отмечены системные роли (флаг, ключ, тип). Права системных ролей нельзя менять, сами роли нельзя удалять. Переименование тоже запрети.
2. **Нельзя менять свою роль.** Участник не может сменить роль самому себе.
3. **Нельзя править роль, которую носишь сам.** Если у текущего пользователя роль X, он не может менять права роли X.
4. **Нельзя выдать больше, чем имеешь.** При изменении прав роли, назначении роли участнику и создании приглашения итоговый набор прав должен быть подмножеством прав текущего пользователя. Исключение: текущий пользователь — продюсер (системная роль с полными правами) или владелец проекта, если в схеме есть такое понятие. Сравнение делай по матрице прав из базы, а не по названию роли.
5. **Последний продюсер.** Нельзя убрать или понизить последнего участника с ролью «Продюсер» в проекте, чтобы проект не остался без управления.
6. **Чужие сущности.** id роли, участника и приглашения проверяй на принадлежность проекту. Если нужно, добавь сущности в `assertInProject` (имена моделей — строго из схемы), ошибку лови через существующий способ в этом файле.
7. **Аудит.** Каждое изменение роли, прав роли, роли участника, удаление участника и создание приглашения записывай в аудит-лог тем же способом, что используется в других модулях (`recordAudit` или `auditMutation` — найди, как устроено). В запись — кто, что, над кем; без телефонов и почт в поле `changes`.

Если какое-то правило невозможно применить из-за устройства кода (например, нет понятия «владелец проекта»), не придумывай обход: опиши это в отчёте.

## ПРОВЕРКА И ОТЧЁТ

2. `npx eslint` по изменённым файлам — без новых ошибок.
