# Аудит PELENA (Film_Prod)

Дата: 21 октября 2026. Режим: только чтение, файлы проекта не менялись.
Этот отчёт собран после прерывания проверки (закончились токены).

Что успело завершиться полностью:

- разведка стека, карта модулей, `tsc --noEmit`, ESLint, `npm audit`;
- секреты в git-истории, авторизация, загрузки файлов, импорт сценария, XSS, миграции;
- **два полных прохода по серверным действиям** — каждое `"use server"`-действие и каждый API-маршрут проверены на права, чужие id и аудит.

Два прохода (мусор и производительность) оборвались, когда выводы уже были сформулированы, а связный текст ещё не написан. Разделы 5 и 6 дописаны по этим выводам. Единственное, чего в заметках нет, — имена примерно десяти неиспользуемых файлов: агент их нашёл, но список остался в выводе команды и в переписку не попал. Этих имён в отчёте нет.

Критичные находки (пункты 1–3 таблицы) перепроверены по коду отдельно, строки совпали.

## 1. Резюме

Платформа рабочая и заметно шире, чем «модуль 1» из README: сценарий, либретто, кастинг, скаут, КПП, вызывные, отчёты, смета, начисления, платежи, договоры. Каркас прав есть и на большинстве действий вызывается. TypeScript собирается без ошибок (`tsc --noEmit` чистый).

Дыры не в «нет авторизации вообще», а в исключениях: несколько действий принимают чужой id и пишут в чужой проект, HTML сценария попадает на страницу без очистки, загрузка файлов доверяет типу, который прислал браузер. Это закрывается точечно, без переписывания архитектуры.

Первые пять задач:

1. Закрыть действия без проверки входа и с чужим id: статус договора, синхронизация либретто, ставки ресурса.
2. Очищать HTML сценария перед сохранением и не отдавать загруженные файлы как страницу сайта.
3. Привязать облачный вход Google/Яндекс к текущей сессии.
4. Проверять, что компания, контрагент, персонаж и сцена из запроса принадлежат этому проекту.
5. Обновить Next.js (сейчас 16.3.2 при известных критичных CVE) и убрать пакет `xlsx` 0.18.5.

## 2. Стек и карта

| Слой | Что стоит |
|---|---|
| Приложение | Next.js 16.3.2 (App Router), React 19, TypeScript 5, Tailwind 4 |
| Вход | Auth.js 5 beta, email + пароль, сессия JWT на 14 дней |
| База | PostgreSQL через Prisma 6. 78 моделей, 41 миграция. Ориентир — Neon |
| Файлы | Локальная папка `storage/`. Cloudflare R2 описан в `.env.example`, в коде не подключён (заглушка) |
| Почта сброса | Resend, если задан `RESEND_API_KEY` |
| Облако | Google Drive и Яндекс.Диск, OAuth, токены шифруются AES-256-GCM |
| Деплой | Vercel (`output: standalone` только вне Vercel) + Dockerfile |
| Пакеты | npm (`package-lock.json`) |
| Языки UI | `next-intl`, словари `messages/ru.json` и `messages/en.json` по 64 ключа, ключи совпадают. Почти весь интерфейс модулей захардкожен по-русски, перевод покрывает только вход, проекты и участников |

Код: `src/app` — страницы и API, `src/features/<модуль>` — действия, запросы, экраны, `src/shared` — база, аудит, UI. Схема — `prisma/schema.prisma` (~1764 строк). Объём: 478 файлов `.ts`/`.tsx`, около 74 тысяч строк.

Паттерны:

- Снимок при утверждении кастинга и скаута есть (`approve-casting.ts`, `approve-scout.ts`). Дальше актёр и локация живут отдельно. Оговорка: при утверждении скаута в живую локацию всё же дописываются адрес и заметки.
- `SceneShootAttempt` задуман как история попыток и пишется из отчёта смены. Это `upsert` по паре сцена+день (`reports/actions.ts`, около строки 224): повторное сохранение факта за тот же день перезаписывает попытку, а не добавляет новую. Отдельного API на удаление попыток нет.
- Обёртка `auditMutation` / `recordAudit` есть, но обязательной не стала. Целиком без аудита: роли, участники и приглашения, смета, версии и комментарии сценария, скаут, почти все локации, часть расписания и постов, загрузки файлов.

## 4. Безопасность подробно

### Секреты

Настоящий `.env` в git не попадал. В истории менялся только `.env.example`. Единственная похожая строка — заглушка `AUTH_SECRET` в примере, её и так надо менять. Поиск по коду паролей и ключей в `src`, `scripts`, `prisma` ничего не дал. `NEXT_PUBLIC_` переменных нет: секретные ключи на клиент не уезжают.

Пример `.env.example` без реальных значений есть. В `docker-compose.yml` пароль базы `filmprod` — это только локальный Postgres, в бой его не брать.

### Вход и сессии

Пароли хешируются bcrypt с стоимостью 12. Сброс: случайные 32 байта, в базе только хеш, срок час, ссылка одноразовая, старые ссылки гасятся. Это сделано правильно.

Слабые места — строки 16–19 таблицы: нет лимита попыток, сессия живёт 14 дней и после смены пароля, ответ «почта не настроена» отличается для существующего ящика. В разработке ссылка сброса печатается в консоль и возвращается на страницу — в бою этого нет, пока `NODE_ENV` не равен `development`.

Промежуточный слой (`src/proxy.ts`) проверяет только язык. Защита страниц проекта идёт в макете через `requireProjectContext`: без участия в проекте страница не откроется. Серверные действия проверяют это сами, кроме пункта 1.

### Чужие проекты

Проверен каждый серверный экшен. Типичная запись сделана верно: членство, право, сущность ищется по id вместе с проектом. Ломается там, где id приходит от браузера и подставляется в `where: { id }` без проекта — пункты 2, 3, 7, 9, 11, 12. Тот же класс у привязок сцены: `locationId`, `characterIds` и `elementIds` в `script/actions.ts` не сверяются с проектом, `sceneId` слота и `actorId` вызывного в `day-docs/actions.ts` тоже.

Финансы в целом закрыты отдельным флагом. Исключение — отчёт смены (пункт 13) и правка ставки актёра через снимок персонажа (`characters/actions.ts`, `updateCharacterCastSnapshotAction`): хватает права на кастинг, финансовое право не спрашивается.

### Ввод и HTML

SQL собирается только в импорте `.kitsp` (это чтение загруженного файла через sql.js, не боевая база), имена таблиц проверяются регулярным выражением. Массовой подстановки полей нет: в базу кладётся уже разобранный объект, а не всё, что прислал браузер.

Единственный опасный HTML — блоки сценария (пункт 4). Текст либретто рисуется обычным текстом, не HTML. Импорт docx берёт текст, не разметку.

### Файлы

Видео проб отдаётся через `/api/projects/.../media/...` только участнику проекта. Это совпадает с задумкой. Публичной корзины нет. Имена на диске — id файла, обхода папок через имя нет.

Дыры другие: тип файла доверяется браузеру (пункт 5), картинки настроек пишутся в `public/uploads` (пункт 21), 512 МБ читаются в память целиком.

### Персональные данные

В базе лежат почта и телефон пользователя, дата рождения, телефоны и почта актёра и агента, телефон контакта локации, ИНН компании и контрагента. Паспортов, СНИЛС и номеров карт в схеме нет.

Кто видит: участник проекта с правом на соответствующий раздел. Отдельного журнала доступа к персональным данным нет. Аудит пишет summary действия, не карточку целиком, но поле `changes` — свободный JSON: надо проследить, чтобы туда не клали телефон и ИНН. Сейчас это не проверялось построчно.

Где физически база, из репозитория не видно. В конфиге ориентир — Neon; регион задаётся в их панели, не в коде. Для 152-ФЗ это нужно выбрать явно (локация в РФ) и зафиксировать у себя, код этого не гарантирует.

Токены Google и Яндекса лежат в базе в зашифрованном виде. Ключ шифрования — секрет приложения (пункт 22).

### Аудит

Записи `AuditLog` никто не обновляет и не удаляет через код. Удаление проекта отвязывает их (`onDelete: SetNull`), не стирает. Пробел — список модулей, которые ничего не пишут (пункт 25).

### Зависимости и заголовки

`npm audit` — 114 записей. Разбор, что из этого реально ваше, в пункте 14 и в абзаце под таблицей. Заголовков безопасности нет (пункт 23). Cookie сессии выставляет Auth.js; отдельных своих cookie с паролем нет.

Миграции деструктивные точечно и все уже в истории: удалялись колонки `status`, `role`, `shiftStartTime`, `locationId`, таблица `EstimateWorkbook` после переноса в листы сметы. Отдельного бэкапа в репозитории нет и не должно быть — его надо иметь на стороне Neon (снимки включены в их платных планах, это вне кода, здесь не проверено).

## 5. Структура и мусор

### Что точно не используется

- `src/features/roles/access.ts` — второй механизм проверки прав, никуда не импортируется. Рабочие два: `requireProjectContext` и `requireProjectAccess`.
- `public/file.svg`, `globe.svg`, `next.svg`, `vercel.svg`, `window.svg` — картинки шаблона Next.js, ссылок нет.
- `@types/bcryptjs` — пакет bcryptjs 3 уже содержит свои типы. `@types/pdfkit` и `@types/sql.js` нужны, но `@types/pdfkit` ошибочно лежит в боевых зависимостях, а не в зависимостях для разработки.
- Маршруты `actors/`, `resources/`, `cast/`, `script/` — старые адреса, они только перенаправляют. Пункт меню на них не ведёт. Страница занятости актёра живёт в `characters/employment`, а `actors/employment` — редирект.

Отдельный проход нашёл ещё около десяти файлов без единого импорта. Имена в заметки не попали, поэтому здесь их нет. Поверхностный поиск по одной только папке `src/features` помечает живые экраны как мёртвые (их подключают страницы из `src/app`), таким списком пользоваться нельзя.

### Дубли, которые агент сверил по файлам

Форматирование денег — функция `money()` объявлена заново в 12 местах: бюджет, начисления, платежи, оба финэкрана, карточка платежа, контрагент, договоры, акты и обе Excel-выгрузки договоров. Сигнатуры уже разъехались: где-то с валютой, где-то без.

Скачивание готового файла (`downloadBase64`) скопировано в каст-лист, либретто, пробы, меню вызывных и кнопку сценария персонажа. Перевод даты в поле ввода (`toDateInput`) — в платежах, начислениях, форме договора и форме акта. Склейка частей строки (`joinParts`) — три раза в вызывных. Экранирование HTML (`escapeHtml`) — в сценарии, вызывном, каст-листе и пробах, то есть ровно там, где от него зависит безопасность. Одно исправление сейчас надо повторять в четырёх файлах.

День/ночь и интерьер/натура разбираются отдельно в импорте сценария, в сборке шапки сцены и в применении либретто.

Выгрузки не сведены к одному конструктору. `features/exports` хранит только набор колонок. Сами файлы собирают семь модулей на ExcelJS (либретто, КПП, вызывной, явочный лист, фин. отчёты, договоры, акты) плюс три своих CSV. Оформление шапки таблицы продублировано между этими файлами. Каст-лист, расписание проб и сценарий собираются через docx. Смету читает отдельный пакет `xlsx`, хотя ExcelJS в проекте уже есть.

### Два модуля там, где кажется, что один

- `budget` — статьи сметы, `smeta` — книга с листами. Оба в меню, хранение разное. Это развилка продукта, а не забытая копия: надо решить, какое главное.
- `script` — таблица сцен (либретто), `screenplay` — постраничный редактор. Маршрут `script/` только перенаправляет в редактор.
- Права выглядят как две системы, но это не так: `memberships/permissions.ts` — перевод старых имён прав («budget:write») в матрицу, которая лежит в базе (`roles/permissions-matrix.ts`). README всё ещё описывает первый файл как саму матрицу. Это устаревшая документация, не второй источник прав.

### Именование и переводы

Файлы в основном через дефис. Выбиваются только суффиксы: у проб, кастинга, расписания и финансов действия разрезаны на `actions-schedule.ts`, `actions-export.ts`, `actions-reports.ts`. На работу не влияет.

Словари `messages/ru.json` и `messages/en.json` совпадают по 64 ключам и покрывают вход, проекты, участников и приглашение. Остальной интерфейс написан по-русски прямо в компонентах, включая группы меню. Английская локаль эти экраны не переведёт. Zod-схемы есть не у каждого модуля: у ролей, контрагентов, сцен, отчётов, локаций, проектов — да; у сметы, проб, скаута и части вызывных поля проверяются вручную.

### Мусор, которого нет

`console.log` в коде нет. `console.error` стоит в обработчиках загрузки и сметы — это серверный лог, не отладка. `TODO` и `FIXME` нет; слово TODO — это статус задачи постпродакшна. В `src/shared/db/prisma.ts` при разработке клиент базы выбрасывается, если в нём нет одной из новых моделей (`company`, `accrual`, `cashPayment` и других). ## 6. Производительность

Эффект оценен по коду, не по замерам: `EXPLAIN` и сборка бандла не запускались.

### База

Индексов в схеме 118, поля `projectId` в основном закрыты. Уже стоят и проверены: почта пользователя, токен сброса пароля, токен приглашения, пара «проект + пользователь», аудит по проекту и дате, составные ключи платежа, начисления и кассового платежа.

Не хватает индекса, и это бьёт по удалению тоже (база при удалении сцены или актёра проверяет связанные строки без индекса):

| Поле | Зачем | Эффект |
|---|---|---|
| `ShootDayScene.sceneId` | «в какие дни входит сцена». Сейчас столбец второй в уникальном ключе, такой поиск идёт по таблице | Высокий |
| `SceneLocation.locationId`, `SceneCharacter.characterId` | страницы локации и персонажа | Средний |
| `ShootDayActorCall.actorId`, `ShootDayResourceUsage.itemId` | занятость актёра и ресурса | Средний |
| `Actor.characterId`, `ActorExtraPayment.actorId` | актёр персонажа и его доплаты. У доплат нет ни индекса, ни уникального ключа | Средний |
| `ProductionReportSceneFact.sceneId`, `ProductionReportWorkRow.locationId` | факт по сцене, строки работ по локации | Низкий |
| `Scene.status` | фильтр либретто по статусу | Низкий |
| `ProjectMembership.roleId`, `ProjectInvite.roleId` и `createdById` | смена роли, список приглашений | Низкий |
| `createdById` у начисления, платежа, файла, пробы | почти не фильтруют | Низкий |

`Certificate.contractId` стоит вторым столбцом после `projectId`: пока запрос начинается с проекта, индекс работает.

Запросы в цикле, которые уже найдены в коде:

- Отчёт смены при открытии пересчитывает строки работ: порядка четырёх запросов на строку, и тут же платежи (`sync-work-rows.ts`). Это и пункт 24 про запись при просмотре.
- Синхронизация ресурсов съёмочного дня делает запись на каждую позицию. Срабатывает при открытии вызывного и при правке сцен.
- Применение либретто и импорт сценария ищут или создают персонажа и локацию по одному на каждую строку. На 200 сценах с пятью персонажами это порядка полутора тысяч запросов.
- Вызывной на каждого актёра делает отдельный поиск и запись.
- Смета в одной транзакции пишет листы по одному, каждый лист — большой JSON.
- Календарь занятости актёров читает одни и те же строки дважды (`serialize-bundle.ts`).
- Страница аудита собирает список пользователей через `distinct`. Prisma делает это в памяти после чтения всех подходящих строк, то есть страница читает журнал шире, чем показывает.

Пагинации нет почти нигде. Она есть у журнала аудита и у договоров. Сцены, платежи, начисления, актёры, локации, файлы, кандидаты кастинга и пробы читаются целиком. Пока проект на десятки записей, это незаметно.

Лишнее в выборке:

- Доска КПП забирает полный текст каждой сцены (пункт 39).
- Вызывной тащит сцену дважды: отдельно и ещё раз внутри каждого таймслота.
- Карточка проекта вместе с матрицей прав и настройками экспорта читается дважды за переход: в макете и на странице. Обёртки `cache()` в проекте нет вообще.
- Операции со сметой (переименование, сохранение как шаблон) перечитывают всю книгу. После автосохранения книга читается ещё раз и уходит обратно в браузер (пункт 42).
- Обзор версий сценария грузит все блоки всех версий, чтобы прикинуть хронометраж.
- Предпросмотр импорта вызывает полный список сцен только ради сверки номеров и кладёт в базу весь разобранный текст вместе с блоками.

### Экраны

Смета. Событие Univer `CommandExecuted` срабатывает почти на любую команду, включая смену выделенной ячейки (`smeta-spreadsheet-editor.tsx:356`). Через 2,5 секунды после последней команды уходит снимок всей книги, на сервере листы удаляются и пишутся заново. Это самый дорогой цикл в приложении.

Либретто. Строки не виртуализированы. Значение ячейки считается дважды, на тысяче сцен и 15 колонках это около 30 тысяч лишних вызовов за одну отрисовку. Поиск без паузы: каждый символ заново фильтрует таблицу. Обработчики строк создаются заново на каждой отрисовке.

Редактор сценария. Каждый символ заново собирает весь массив блоков, заново считает хронометраж и разрывы страниц и кладёт полную копию в историю правок. Строки не обёрнуты в память, поэтому перерисовываются все. Списки персонажей и локаций для подсказок создаются заново в каждой строке. Сохранение отправляет все блоки, сервер их стирает и создаёт снова.

Доска КПП. Пока карточку тащат, заново пересчитываются сводки всех дней. Карточки дней не запомнены. До примерно 60 смен терпимо, дальше будет дёргаться.

Вызывной в режиме правки. Семь массивов состояния, шесть `JSON.stringify` прямо во время отрисовки: любой ввод в одно поле перерисовывает и заново сериализует все разделы.

Платежи, начисления и бюджет-статьи. Фильтр отправляется формой, а не на каждый символ, лишних перерисовок нет. Списки без страниц: тормозить начнут на сотнях строк, не раньше. Итоги платежей и начислений считаются вторым полным чтением того же списка.

`router.refresh()` есть на смете, в редакторе сценария, вызывном, карточке договора и файлах, но не на каждый символ. `revalidatePath` в сценах и расписании сбрасывает несколько адресов за раз. Страницы и так динамические из-за сессии, поэтому это чистит кэш перехода, а не пересобирает всё дерево. Эффект низкий.

### Бандл

| Библиотека | Куда попадает | Что с этим делать |
|---|---|---|
| Univer | только экран сметы, статически. Самый тяжёлый кусок, и он там нужен | Не импортировать его больше нигде. В `transpilePackages` не хватает `@univerjs/themes`, он подтягивается транзитивно |
| ExcelJS | в браузер на либретто, договорах, актах и в окне выгрузки КПП. Ещё три выгрузки (вызывной, явочный, фин. отчёты) остаются на сервере | Четыре клиентские сборки перенести в серверное действие, как уже сделано у вызывного |
| `xlsx` | только сервер, импорт сметы | Удалить после перехода на ExcelJS. На размер страницы не влияет |
| `@dnd-kit` | десять клиентских экранов, статически | Лёгкий, трогать не стоит |
| `docx` | каст-лист, пробы, сценарий. Часть импортов статическая из клиентского модуля | Попадёт ли сам пакет в браузер, без сборки не видно. Выгрузки лучше собирать на сервере |
| `pdfkit` | динамический импорт, сервер | Нормально |
| `mammoth`, `suncalc` | только сервер | Нормально |
| `sql.js` | динамический импорт, только разбор `.kitsp` | Нормально. Попадёт ли wasm-файл в Docker-образ standalone, не проверялось: в `serverExternalPackages` пакет указан |

### Импорт и запись

Очереди нет, разбор идёт внутри запроса. Смета кодирует файл в base64 (+33% к размеру) и разбирает его синхронно. Предел тела серверного действия в конфиге не поднят, у Next он по умолчанию около 1 МБ, то есть файл сметы крупнее примерно 750 КБ, скорее всего, не сохранится. Это не проверено запросом.

Импорт сценария читает файл в память целиком, docx разбирается дважды (текст и блоки), и весь предпросмотр пишется в JSON-поле задания.

Выгрузки pdf и xlsx собираются в памяти и возвращаются на страницу как base64 без потолка размера. Сохранение версии сценария стирает блоки и создаёт их заново, на большом сценарии это тысячи строк за одно сохранение.

Prisma при обрыве соединения повторяет любой запрос до трёх раз, включая создание записи (пункт 32). Отдельного адаптера Neon нет, пул соединений в коде не настроен: клиент берёт обычную строку `DATABASE_URL`. В бою один процесс может поднять несколько копий клиента, потому что одиночка кладётся в `globalThis` только в разработке. Медленные запросы не логируются.
