## РОЛЬ И КОНТЕКСТ

Ты исправляешь уязвимости в мультипроектной SaaS-платформе для кинопроизводства. Стек: Next.js 16 (App Router, server actions), React 19, TypeScript, Prisma 6, PostgreSQL. Пользователь одного проекта не должен ни видеть, ни менять данные другого.

В прошлом пакете создан помощник `src/features/memberships/assert-in-project.ts` с функцией `assertInProject(entity, ids, projectId, tx?)`. Прочитай этот файл перед началом, а также `docs/audit/FIX_REPORT_1.md`: там описано, как устроены проверки и что уже исправлено.

## СУТЬ ПРОБЛЕМЫ

Серверные действия принимают из браузера id связанных сущностей: контрагента, компании, статуса, персонажа, сцены, локации, актёра и т.д. Они пишут эти id в базу или меняют запись по ним, не проверяя, что сущность из этого же проекта. Так участник проекта А может привязать или изменить данные проекта Б.

Есть два вида ошибки:
1. **Запись по голому id:** `update` или `delete` с `where: { id }` без проверки проекта.
2. **Чужой внешний ключ:** при `create` или `update` в поле вида `counterpartyId`, `characterId`, `sceneId`, `locationId`, `tagIds` и т.п. (или в `connect`) записывается id из браузера без проверки проекта.

## ЖЁСТКИЕ ПРАВИЛА

1. Меняй только файлы, перечисленные в задачах ниже, и `assert-in-project.ts`. Если для исправления нужен другой файл (например, вызов функции, у которой поменялась сигнатура), можно менять, но в отчёте перечисли все такие файлы и объясни зачем.
2. Никакого рефакторинга, переименований и переформатирования файлов целиком, кроме того, что прямо разрешено в части A.
3. Не меняй `prisma/schema.prisma`, не создавай миграции, не запускай команды Prisma, которые меняют базу (`migrate`, `db push`, `db seed`, `migrate reset`).
4. Не меняй интерфейс и тексты на экране.
5. Не удаляй и не ослабляй существующие проверки прав.
6. `projectId` всегда бери из проверенного контекста (`requireProjectContext` / `requireProjectAccess`), никогда из данных браузера.
7. Необязательные ссылки (`null`, `undefined`, пустая строка, пустой массив) не проверяй: их просто нет.
8. Все id одного вида проверяй одним вызовом `assertInProject` с массивом, не в цикле.
9. Проверки делай **до** первой записи в базу. Если хоть одна ссылка чужая, ничего не должно записаться.
10. Номера строк примерные. Ищи по имени функции. Если код не совпадает с описанием, не додумывай: опиши расхождение в отчёте и переходи к следующей задаче.
11. Не делай git commit и git push.
12. Не останавливайся на полпути и не пиши «остальное аналогично». Каждая задача делается полностью или явно помечается в отчёте как пропущенная с причиной.

Для каждой модели выясни по схеме, есть ли прямой `projectId` или проект определяется через связь, и задай фильтр соответственно. Скорее всего понадобятся: компания, контрагент, статус согласования, тип договора, тег договора, договор, платёж, персонаж, актёр, элемент сцены (реквизит, костюм и т.п.), съёмочный день, кандидат кастинга, проба. ## ЧАСТЬ D — сцены: либретто, сценарий, синхронизация

### D1. Привязки сцены в либретто
**Файл:** `src/features/script/actions.ts`.
**Проблема:** при создании и изменении сцены `locationId`, `characterIds` и `elementIds` из браузера не сверяются с проектом.
**Сделать:** в каждом действии, которое создаёт или меняет сцену либо её привязки, до записи проверь локацию, персонажей и элементы через `assertInProject`. Также проверь, что сама изменяемая сцена из этого проекта.

### D2. Синхронизация сценария и сцен
**Файл:** `src/features/screenplay/lib/sync.ts` и действия, которые его вызывают.
Из описи прошлого пакета:
- `syncSceneFromSlugline` (около строки 123) — получает id сцены и проект, но сцену на проект не проверяет;
- `syncSceneScriptContent` (около строки 171) — обновляет сцену только по id;
- `syncSluglineFromScene` (около строки 202) — загружает сцену по голому id и правит блок сценария; действие `syncSceneSluglineAction` проверяет участника, но не сцену;
- `ensureScenesFromBlocks` — если в блоке с клиента уже есть `sceneId`, он принимается как есть.

**Сделать:**
1. В `update` сцены добавь `projectId` в `where`.
2. Если функция не получает `projectId`, добавь его параметром и передай из всех мест вызова. В вызывающем коде `projectId` должен быть уже проверенным.
3. В `syncSluglineFromScene` загружай сцену с условием по `projectId`. Блок сценария правь только если он принадлежит версии этого же проекта.
4. В `ensureScenesFromBlocks` все `sceneId`, пришедшие с клиента, проверь одним вызовом `assertInProject`. Если сцена чужая или не найдена, не доверяй этому `sceneId`. Как поступить — вернуть ошибку или обработать блок как без `sceneId` — реши по тому, что делает функция для блока без `sceneId`, и опиши выбор в отчёте.
5. В `syncSceneSluglineAction` проверь сцену через `assertInProject`.

### D3. Версия сценария в синхронизации либретто

**Проблема:** сцены проверяются (это сделано в прошлом пакете), а `versionId` из браузера, судя по коду, нет. По нему читаются и связываются блоки версии.
**Сделать:** проверь `versionId` через `assertInProject` до любого чтения и записи. Если проверка уже есть, ничего не меняй и так и напиши.

Заодно пройди остальные действия в `src/features/screenplay/actions.ts`, которые принимают `versionId` или `blockId`. Где проверки нет — добавь.
