# ЧАСТЬ 1. ИНСТРУКЦИЯ

## Подготовка

**1. Убери отчёт аудита из папки проекта.** Скопируй `AUDIT_REPORT.md` куда-нибудь в Документы. Он понадобится позже, а при откате изменений может удалиться.

**2. Создай ветку под пакет.** В терминале Cursor:
```
git checkout main
git status

```
Если основная ветка называется `master`, пиши `master` вместо `main`. Если `git status` пишет, что есть несохранённые изменения, остановись и пришли мне его вывод.

**3. Проверь, к какой базе подключён проект у тебя на компьютере.** Открой `.env` и найди строку `DATABASE_URL`. Если там адрес Neon (`...neon.tech...`), значит локальная версия работает с той же базой, что и сайт. Промпты запрещают любые команды, меняющие базу, но запомни: всё, что ты создашь при ручной проверке, появится и на сайте. Позже заведём отдельную базу для разработки.

**4. Не пуш в main до моей проверки.** Если Vercel подключён к GitHub, пуш в main сразу выкатит изменения на сайт.

**5. В Cursor:** режим Agent, модель Grok 4.7, выбранная вручную, а не auto.

# ЧАСТЬ 3. ПРОМПТ 2 — исправления безопасности

## РОЛЬ

Ты исправляешь найденные аудитом уязвимости в SaaS-платформе для кинопроизводства. Стек: Next.js 16 (App Router, server actions), React 19, TypeScript, Prisma 6, PostgreSQL. Платформа мультипроектная: пользователь одного проекта не должен ни видеть, ни менять данные другого проекта.

Владелец проекта не программист. Код пишется через AI. Твоя задача — точечные исправления, а не рефакторинг.

## СУТЬ ПРОБЛЕМЫ

В нескольких серверных действиях id сущности приходит из браузера и подставляется в запрос как `where: { id }` без проверки, что эта сущность принадлежит проекту пользователя. Участник проекта А может подставить id из проекта Б и изменить чужие данные. Ещё одно действие экспортировано из файла `"use server"` и вообще не проверяет вход.

## ЖЁСТКИЕ ПРАВИЛА

1. Меняй только файлы, перечисленные в задачах ниже. Исключения: новый файл помощника (часть A) и файлы, которые импортируют перенесённую функцию (задача B1).
2. Никакого рефакторинга, переименований, переформатирования файлов целиком и «заодно улучшил». Заметил другую проблему — запиши её в отчёт и не трогай.
3. Не меняй `prisma/schema.prisma`, не создавай миграции, не запускай команды Prisma, которые меняют базу (`migrate`, `db push`, `db seed`, `migrate reset`).
4. Не меняй интерфейс и тексты на экране.
5. Не удаляй и не ослабляй существующие проверки прав.
6. `projectId` всегда бери из проверенного контекста, то есть из результата существующей проверки участника проекта. Никогда не бери его из данных, пришедших от браузера.
7. Номера строк указаны примерно и могли сдвинуться. Ищи по имени функции. Если код не совпадает с описанием (функции нет, логика другая), не додумывай: пропусти задачу, опиши расхождение в отчёте и переходи к следующей.
8. Не делай git commit и git push.

## ЧАСТЬ A — общий помощник проверки

Создай файл `assert-in-project.ts` рядом с файлом, где лежит `requireProjectAccess`.

Требования:
- Первая строка файла: `import "server-only";`
- Функция `assertInProject(entity, ids, projectId, tx?)`:
  - `entity` — строковое имя сущности из фиксированного набора. Для этого пакета нужны: сцена, версия сценария, комментарий сценария, локация, фото локации, позиция ресурса. Используй реальные имена моделей из схемы. Сделай так, чтобы новую сущность можно было добавить одним новым `case`.
  - `ids` — один id или массив. Убери дубли. Пустой массив считается успехом.
  - Один запрос к базе на вызов: посчитать записи, у которых id входит в список и которые принадлежат проекту. Если у модели нет прямого `projectId`, фильтруй через связь по схеме.
  - Если найдено меньше записей, чем уникальных id, отказ. Сообщение одинаковое для «не существует» и «из чужого проекта»: «Объект не найден». Нельзя по ответу понять, существует ли чужой объект.
  - Способ отказа такой же, как у `requireProjectAccess`.
  - `tx` — необязательный клиент транзакции Prisma, чтобы функцию можно было вызывать внутри `$transaction`.
- Добавь короткий комментарий на русском над функцией: зачем она и когда её вызывать.

## ЧАСТЬ B — исправления

### B1. Действие без проверки входа

**Где:** `src/features/contracts/actions.ts`, функция `resolveDefaultStatusIdAction`, около строки 633.

**Проблема:** функция экспортирована из файла с `"use server"`. В таком файле каждая экспортированная async-функция становится публичной точкой доступа из браузера. Проверки входа в ней нет, поэтому её можно вызвать с любым id проекта и создать там служебные статусы.

**Сделать:**
1. Найди поиском по проекту все места, где вызывается эта функция.
2. Если она вызывается **только из серверного кода** (страницы, другие действия, серверные `lib`), перенеси её в новый файл `src/features/contracts/lib/default-status.ts` с `import "server-only";` и без `"use server"`. Убери суффикс `Action` из имени, обнови все импорты и удали функцию из `actions.ts`.
3. Если она вызывается **из клиентского компонента**, оставь её действием, но в самом начале добавь ту же проверку участника и права, что у соседних действий с договорами. `projectId` бери из результата проверки.

### B2. Синхронизация либретто пишет в чужие сцены

**Где:** `src/features/screenplay/lib/libretto-apply.ts`, около строки 137, и действие, которое её вызывает.

**Проблема:** сцена обновляется по id из данных браузера без проверки проекта. Можно переписать текст, хронометраж, локации и персонажей сцены в чужом проекте.

**Сделать:**
1. Проследи, откуда приходят id сцен.
2. **До любой записи** собери все id сцен из входных данных и вызови `assertInProject` для сцен. Если хоть одна чужая, отклони всю операцию целиком: ничего не должно записаться.
3. Дополнительно в самих запросах на изменение и удаление сцены добавь `projectId` в `where` рядом с `id`, если у модели есть прямое поле `projectId`. Prisma 6 это позволяет.
4. Логику создания и поиска персонажей и локаций внутри синхронизации **не трогай**: это следующий пакет. Только упомяни её в отчёте.

### B3. Ставки ресурса меняются в чужом проекте

**Где:** `src/features/resources/actions.ts`, около строки 330: действие, которое удаляет и создаёт ставки переработок и доплат позиции ресурса.

**Проблема:** ставки удаляются и создаются по id позиции без проверки, что позиция из этого проекта.

**Сделать:**
1. В начале действия, до удаления ставок, вызови `assertInProject` для позиции ресурса.
2. Проверь, какое право требует это действие. Если для финансовых ставок хватает права на ресурсы без финансового права, **не меняй это**, а запиши в отчёт: этим займётся отдельный пакет.

### B4. Ответ на комментарий в чужой версии сценария

**Где:** `src/features/screenplay/actions.ts`, около строки 649: действие ответа на комментарий.

**Проблема:** не проверяется, что версия сценария из этого проекта.

**Сделать:**
1. Проверь через `assertInProject`, что версия из этого проекта.
2. Если передаётся id родительского комментария, проверь, что этот комментарий относится **к той же версии**. Если нет, отказ с тем же сообщением «Объект не найден».

### B5. Фото чужой локации

**Где:** `src/features/locations/actions.ts`, около строк 166 (добавление фото) и 180 (удаление фото).

**Проблема:** не проверяется, что локация из этого проекта.

**Сделать:**
1. **Добавление:** до записи вызови `assertInProject` для локации.
2. **Удаление:** найди фото по id с условием, что его локация принадлежит проекту. Не нашлось — отказ. Удалять файл из хранилища только после успешной проверки.
