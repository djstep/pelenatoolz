**Переменная окружения с секретом: `CLOUD_TOKEN_SECRET` (если её нет — берётся `AUTH_SECRET`). В production одна из них обязательна и должна быть не короче 32 символов.**

# Отчёт по пакету 3

Выполнил Claude Code по ТЗ `docs/audit/tasks/package-3-5-security.md`, часть 2 («Промпт 3»).

## Перед переносом в main — что проверить на Vercel

Project → Settings → Environment Variables:

1. Задан ли `CLOUD_TOKEN_SECRET`.
   - **Задан** — ничего не меняется. Проверьте только, что он не короче 32 символов.
   - **Не задан** — ключ берётся из `AUTH_SECRET`, как и раньше. Уже подключённые диски продолжат работать. Проверьте, что `AUTH_SECRET` не короче 32 символов.
2. Если нужный секрет короче 32 символов, после переноса подключение дисков, список файлов и выбор файла из облака будут падать с ошибкой «Не задан секрет шифрования облачных дисков». Остальной сайт продолжит работать.
3. **Не задавайте** новый `CLOUD_TOKEN_SECRET`, если его раньше не было. Иначе ключ сменится, и все подключённые Google/Яндекс Диски придётся подключать заново. Отдельный секрет можно завести позже, понимая, что диски придётся переподключить.

## Как код был устроен на самом деле

ТЗ предполагало: если секрет не задан, используется известная строка. На деле цепочка была такая: `CLOUD_TOKEN_SECRET`, если его нет — `AUTH_SECRET` (секрет входа Auth.js, на Vercel он задан всегда), и только если нет обоих — `dev-cloud-secret-change-me`. Значит, токены на сайте, скорее всего, зашифрованы через `AUTH_SECRET`. Владелец выбрал оставить цепочку и запретить в production только известную строку и короткий секрет.

Ещё одно расхождение. Адрес возврата `returnTo` клиент передаёт относительным (`/ru/projects/...`), а callback делал `NextResponse.redirect("/ru/...?cloud_connected=...")`. Next.js принимает в этом методе только полный адрес и на относительном падает с ошибкой «URL is malformed». То есть после согласия в Google или Яндексе диск в базу записывался, а пользователь, скорее всего, видел ошибку вместо возврата на страницу. В браузере это не проверял, вывод сделан по коду Next.js. Теперь callback собирает полный адрес: `appOrigin()` плюс проверенный путь. Это и есть место применения `safeRedirectPath` из задачи 2.

## Задача 1. Облачный диск привязывается к чужому аккаунту

- **Что было:** callback Google и Яндекса проверял только подпись `state` и записывал подключение на `userId` из `state`. Текущая сессия не сверялась, срока жизни у `state` не было.
- **Что сделано:**
  - В `state` добавлено поле `issuedAt`, время выпуска. `verifyOAuthState` отклоняет `state` старше 10 минут, без `issuedAt` или из будущего (запас на часы — 1 минута).
  - В callback, до обмена кода на токен, берётся сессия через `auth()`. Нет сессии или её пользователь не совпадает с `userId` из `state` — редирект на `/ru/projects?cloud_error=state`, как при неверном `state` сейчас. В базу ничего не пишется, код у Google/Яндекса не обменивается.
- **Изменённые файлы:**
  - `src/features/cloud/lib/token-crypto.ts`
  - `src/app/api/cloud/google/callback/route.ts`
  - `src/app/api/cloud/yandex/callback/route.ts`
  - Маршруты `authorize` вызывают `signOAuthState` как раньше: время выпуска функция ставит сама.

## Задача 2. Редирект на чужой сайт

- **Что было:** после входа и регистрации адрес возврата проверялся только на `startsWith("/")`, поэтому `//чужой-сайт.ru` проходил. В облачных маршрутах `returnTo` не проверялся совсем.
- **Что сделано:** новый файл `src/shared/lib/safe-redirect.ts` с функцией `safeRedirectPath(input, fallback)`. Путь проходит, только если это строка, которая:
  - начинается ровно с одного `/`;
  - вторым символом не имеет `/` или `\`;
  - нигде не содержит `\` и управляющих символов (коды 0–31 и 127–159);
  - не длиннее 2000 символов.

  Иначе возвращается `fallback`.
- **Где применена:**

| Файл | Место | Фолбэк |
| --- | --- | --- |
| `src/features/auth/actions.ts` | `registerAction`, `callbackUrl` после регистрации | `/ru/projects` |
| `src/features/auth/actions.ts` | `loginAction`, `callbackUrl` после входа | `/ru/projects` |
| `src/app/api/cloud/google/authorize/route.ts` | `returnTo` перед записью в `state` | `/ru/projects` |
| `src/app/api/cloud/yandex/authorize/route.ts` | `returnTo` перед записью в `state` | `/ru/projects` |
| `src/app/api/cloud/google/callback/route.ts` | `returnTo` из `state` перед редиректом | `/ru/projects` |
| `src/app/api/cloud/yandex/callback/route.ts` | `returnTo` из `state` перед редиректом | `/ru/projects` |

- **Без `returnTo` вовсе** `authorize` по-прежнему отвечает 400, как раньше. Если `returnTo` есть, но не проходит проверку, используется фолбэк.
- **Пути с языком** (`/ru/invite/...`, `/ru/projects/...`) проходят без изменений. Проверил на наборе адресов, в том числе `//evil.com`, `/\evil.com`, `https://evil.com`, `/<TAB>/evil.com`, пустая строка и не-строка: все чужие дают фолбэк.
- **Другие места**, где адрес возврата берётся из запроса или формы, поиском не нашлись. Остальные `redirect` и `router.push` строят адрес в коде.

## Задача 3. Известный ключ шифрования по умолчанию

- **Что было:** `CLOUD_TOKEN_SECRET ?? AUTH_SECRET ?? "dev-cloud-secret-change-me"` и для шифрования токенов, и для подписи `state`.
- **Что сделано** (в `src/features/cloud/lib/token-crypto.ts` одна функция `cloudSecret()` вместо двух копий):
  - Порядок прежний: `CLOUD_TOKEN_SECRET`, иначе `AUTH_SECRET`. Пустая строка теперь считается «не задано».
  - При `NODE_ENV === "production"`, если секрета нет или он короче 32 символов, бросается ошибка «Не задан секрет шифрования облачных дисков: укажите CLOUD_TOKEN_SECRET (или AUTH_SECRET) длиной не меньше 32 символов». Проверка срабатывает при шифровании, расшифровке, подписи и проверке `state`, а не при импорте. Сборка без секрета проходит, это проверено.
  - В разработке без секрета остаётся ключ для разработки и один раз пишется `console.warn`.
- **Проверено скриптом:** свежий `state` принимается; `state` старше 11 минут, без `issuedAt` и с испорченной подписью отклоняются; шифрование и расшифровка дают исходную строку; в production с секретом из 5 символов и без секрета — понятная ошибка.

## Замечено, но не тронуто

- `.env.example` не упоминает `CLOUD_TOKEN_SECRET`. Стоит дописать строку с пояснением. Файл не из списка задачи.
- Подпись `state` сравнивается обычным `!==`, а не сравнением за постоянное время (`timingSafeEqual`). Риск низкий: подпись HMAC, и `state` теперь живёт 10 минут.
- `projectId` в `authorize` берётся из адреса и кладётся в `state` без проверки участия в проекте. В callback он не используется: подключение диска привязано к пользователю, не к проекту. Утечки нет, но поле лишнее.
- В callback к адресу возврата всегда дописывается `?cloud_...`. Если в `returnTo` уже есть `?`, получится второй `?`. Сейчас клиент передаёт пути без параметров.
- Ключ шифрования дисков совпадает с секретом входа, когда `CLOUD_TOKEN_SECRET` не задан. Лучше иметь отдельный, но смена ключа требует переподключить все диски (см. начало отчёта).
