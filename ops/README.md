# Рабочий сервер

Сайт `https://pelena.space`, сервер cloud.ru, папка проекта `~/pelena`. Копии и восстановление описаны
в [backup/README.md](backup/README.md), запуск контейнеров — в шапке `docker-compose.prod.yml`.

## Обновление сайта

На сервере одна команда:

```bash
sudo pelena-deploy
```

Берёт код из `main`. Другая ветка: `sudo pelena-deploy feat/vps-docker`.

Порядок:

1. Свежая копия базы и файлов. **Если копия не удалась, обновление не начинается, сайт не трогается.**
   Имя копии команда печатает: запишите его, если обновление пойдёт плохо.
2. Код из ветки. Если история разошлась с сервером или в ветке нет настроек сервера, обновление останавливается.
3. Сборка образов.
4. Миграции от `pelena_owner`. Права на новые таблицы сайт получает сам.
5. Перезапуск сайта.
6. Проверка ответа сайта, включая чтение базы.

На шагах 3 и 4 при сбое сайт продолжает работать на прежней версии. Если миграция прошла частично,
смотрите её вывод: схема могла измениться. Настройки nginx команда не меняет: для этого есть `ops/nginx/setup.sh`.

## Откат

Сначала посмотрите, были ли в обновлении миграции: код откатывается легко, схема базы — нет.

Без миграций, из папки проекта:

```bash
git checkout <прежний коммит>
docker compose --profile tools build app migrate
docker compose up -d app
```

С миграциями восстанавливайте именно копию из вывода обновления: самая новая могла быть сделана уже после
плохой миграции.

```bash
sudo pelena-backup-restore <файл>.dump.age
```

Перед этим верните код, иначе плохая миграция применится снова. Подробности в [backup/README.md](backup/README.md).
Данные, внесённые после копии, останутся только в старой базе `pelena_before_restore`.

## Перенос картинок в `storage/uploads`

Разовый шаг при первом обновлении, где `/uploads/` отдаёт сайт. Команды выполняются из папки проекта.
Порядок важен: команда обновления идёт первой, потому что её копия ещё обходит старую папку. Если сайт уже
создал новую папку, `cp -an` дополняет её и ничего не перезаписывает, а простой `mv` положил бы всё во
вложенную папку.

```bash
sudo pelena-deploy
sudo mkdir -p /mnt/data/storage/uploads
sudo cp -an /mnt/data/uploads/. /mnt/data/storage/uploads/
sudo chown -R 1001:1001 /mnt/data/storage
sudo find /mnt/data/uploads -type f | wc -l
sudo find /mnt/data/storage/uploads -type f | wc -l
sudo bash ops/nginx/setup.sh
sudo systemctl start pelena-backup.service
sudo pelena-backup-restore-test
```

Запрос к картинке без входа должен дать 401. Пока не выполнен `setup.sh`, старый nginx отдаёт старые картинки
без входа, а новые не находит. Папка `/mnt/data/uploads` и `files:uploads` в облаке больше не обновляются,
удалять их только после решения владельца.

При откате на версию до этого шага верните картинки и запустите `setup.sh` уже на прежнем коде:

```bash
sudo cp -an /mnt/data/storage/uploads/. /mnt/data/uploads/
sudo bash ops/nginx/setup.sh
```

## Ключи дисков

```bash
sudo pelena-oauth
```

Секреты вводятся скрыто и попадают только в `.env.prod`. Пустой ввод оставляет ключи сервиса как есть.
Сайт перезапускается сам, при сбое прежние ключи возвращаются. После смены сохраните `.env.prod` в менеджере паролей.

Адреса возврата в консолях Google и Яндекса:

```text
https://pelena.space/api/cloud/google/callback
https://pelena.space/api/cloud/yandex/callback
```

## Nginx и сертификат

```bash
sudo bash ops/nginx/setup.sh
```

Команда проверяет DNS, ставит nginx и `certbot`, выпускает один сертификат на `pelena.space` и `www.pelena.space`.
Без подтверждения DNS она останавливается. Настройки — `ops/nginx/pelena.conf`.

- `https://pelena.space` — основной адрес.
- `www` и `http` — постоянный редирект на него.
- Картинки `/uploads/` отдаёт сайт и только активным участникам проекта. Лежат в `/mnt/data/storage/uploads`.
- Большие тела запросов принимаются только на адресах загрузки файлов, вход там проверяется раньше чтения тела.
- Частота POST ограничена для одного адреса: 10 в секунду с запасом 40. Сверх этого ответ 429.
- Сертификат продлевается сам (`certbot.timer`), nginx после этого перечитывает его.

Правка настроек: измените файлы в `ops/nginx/`, обновите сайт и запустите `sudo bash ops/nginx/setup.sh`.

Проверка продления: `sudo certbot renew --dry-run`.

В группе безопасности cloud.ru открыты входящие TCP 22, 80, 443. Порт сайта 3000 и порт базы наружу закрыты.
Сертификат выпущен без почты: писем об окончании срока не будет, за продлением следит `certbot.timer`.
